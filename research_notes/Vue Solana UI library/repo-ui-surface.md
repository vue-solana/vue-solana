# Vue Solana UI Library — Existing Surface and Architectural Constraints

## 1. Which existing files are already reusable UI building blocks or close to components?

### Takeaway

The repo already has a rich **application-level** UI layer and a polished headless state layer, but almost no shipped component layer: the only component in a published package is a renderless provider, while the docs/examples contain the reusable shells, panels, props/emit contracts, and presentation logic a UI package would be built from.

### Cited Findings

- The only exported component in a published package is `SelectedWalletAccountProvider`, which is explicitly a provider wrapper around `provideSelectedWalletAccount()` and returns only `slots.default?.()` — no DOM, no styling, and no picker UI ([SelectedWalletAccountProvider.ts:7-35](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/components/SelectedWalletAccountProvider.ts#L7), [vue/src/index.ts:43](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/index.ts#L43)).
- The docs app has reusable presentational shells: `DemoPanel` accepts `eyebrow`, `title`, `status`, `statusColor`, `wide` and wraps a slot in `UCard`/`UBadge`, so it is effectively a styled card primitive tied to `@nuxt/ui` tokens ([DemoPanel.vue:1-43](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoPanel.vue#L1)); `DemoDataGrid`, `DemoSection`, `DemoSectionTabs`, `DemoHero`, `DemoLiveCard`, and `DemoSignInCard` in the same directory split data/status props from display (examples: [DemoWalletPanel.vue:3-40](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoWalletPanel.vue#L3), [DemoSignInCard.vue:4-55](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoSignInCard.vue#L4)).
- The docs demo already uses a **headless composable + dumb component** split: `useDemoWallet()` owns `computed` status/color/enablement, wallet actions, clipboard, and `useToast()` messages, then returns a flat API for the SFC ([useDemoWallet.ts:5-120](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/composables/demo/useDemoWallet.ts#L5)); `DemoWalletPanel.vue` declares pure props (`canConnect`, `statusText`, `wallets`, …) and emits `connect`, `disconnect`, `selectWallet`, `copyAddress`, etc. ([DemoWalletPanel.vue:3-25](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoWalletPanel.vue#L3)).
- `ShowcaseApp.vue` is an MDC component whose slot text is translated per locale while its labels come from the `showcase.*` i18n branch; it shows the exact pattern a shipped UI component would need for user-visible copy and icons ([ShowcaseApp.vue:1-64](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/content/ShowcaseApp.vue#L1), [AGENTS.md:202](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L202)).
- Both examples mount a full set of Solana panels — wallet discovery/connect, balance, RPC status, direct RPC, transfer, mock transaction, message signing, signers, Solana Pay request/QR, Solana Pay scanner, simulation, transaction history, live data, SWR — so these are working reference implementations of a future component catalog ([AGENTS.md:238-244](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L238), [examples/vue-vite/src/App.vue:1-17](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/App.vue#L1)).
- `WalletPanel.vue` is the closest thing to a wallet-connect component: it computes `walletStatusText`, `walletStatusClass`, `canConnectWallet`, `canDisconnectWallet`, renders a discovered-wallet list with icons, and handles connect/disconnect/copy errors through a shared `formatError()` helper ([WalletPanel.vue:6-105](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/WalletPanel.vue#L6), [WalletPanel.vue:169-220](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/WalletPanel.vue#L169)).
- `SolanaPayPanel.vue` and `SolanaPayScannerPanel.vue` are close to payment-flow components: the first composes `useSolanaPay()` + `useSolanaQrCode()` + `useSolanaPayConfirmation()` and adds amount parsing, validation, status, and verification display ([SolanaPayPanel.vue:29-188](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayPanel.vue#L29)); the second wraps camera/paste validation and deliberately refuses to auto-send, showing only a `solana:` link ([SolanaPayScannerPanel.vue:20-93](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L20), [SolanaPayScannerPanel.vue:112-116](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L112), [SolanaPayScannerPanel.vue:214-229](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L214)).

- `LiveDataPanels.vue` is raw wiring for `useRequest()`, `useSubscription()`, `useTrackedData()`, `useSignIn()`, `usePayer()`, and the send hooks; it is the clearest evidence that live-data UI is still app-owned rather than packaged ([LiveDataPanels.vue:24-103](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/LiveDataPanels.vue#L24), [repo-gap-audit.md:58](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md#L58)).
- The shipped API is already close to headless UI state: `useWallet()` returns `publicKey`, `connected`, `connecting`, `canSign*` flags, `capabilities`, and normalized errors ([useWallet.ts:78-114](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useWallet.ts#L78)); `useWallets()` is a thin wrapper over discovery/selection state ([useWallets.ts:3-12](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useWallets.ts#L3)); `useSignIn()` exposes `status`, `loading`, `error`, and `signInResult` ([useSignIn.ts:7-53](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSignIn.ts#L7)); `useSolanaPay()` exposes request URL, parsed request, reference, status, loading, error, and reset ([useSolanaPay.ts:11-109](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaPay.ts#L11)); `useSolanaPayConfirmation()` owns polling and cleanup ([useSolanaPayConfirmation.ts:4-44](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaPayConfirmation.ts#L4)).
- QR is already a packaged UI-adjacent capability: `useSolanaQrCode()` renders an SVG through core's lazy `createQR()` ([useSolanaQrCode.ts:1-33](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaQrCode.ts#L1)); `useSolanaQrScanner()` owns camera, `BarcodeDetector`, `jsqr` fallback, focus constraints, parsing, lifecycle cleanup, and a browser-only guard ([useSolanaQrScanner.ts:26-68](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaQrScanner.ts#L26), [useSolanaQrScanner.ts:217-308](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaQrScanner.ts#L217)).
- The e2e suite already treats the panels as a UI contract: it asserts wallet disabled states, signer addresses and real signatures, scanner preview/amount/label/`solana:` link, and scanner camera status through `data-testid`s ([e2e/example-apps.spec.ts:62-84](/Users/mohsenpakfetrat/Development/vue-solana/e2e/example-apps.spec.ts#L62), [e2e/example-apps.spec.ts:152-188](/Users/mohsenpakfetrat/Development/vue-solana/e2e/example-apps.spec.ts#L152), [e2e/example-apps.spec.ts:516-576](/Users/mohsenpakfetrat/Development/vue-solana/e2e/example-apps.spec.ts#L516)).
- The earlier planning report ranked a "Headless wallet picker / UI package" 8th of its options at 54 points and explicitly called out "CSS/a11y/SSR/mobile handoff and a second versioning surface" as product-pivot cost ([Next Vue Solana feature.md:36](/Users/mohsenpakfetrat/Development/vue-solana/reports/Next%20Vue%20Solana%20feature.md#L36), [strategy-feasibility.md:149](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L149)); its final boundary advice was to keep the first slice composable-only and let apps own presentation ([strategy-feasibility.md:189](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L189)).

### Inferences

- The cheapest reuse path is to promote the docs' existing props/emit view components and demo composables into documented headless APIs rather than writing a modal from scratch; the logic and visual contracts already exist in two example apps and the docs demo.
- QR render/scan are already the most "component-ready" surface: the lifecycle, error, and browser guards live in composables, so a UI package could add only markup.
- A wallet-connect UI would have the most evidence and the most liability: the state layer is mature, but mobile handoff, capability messaging, and translated copy are already app responsibilities.

### Gaps

- No file in the repo is a shipped, styleable modal/dialog/picker; exact a11y behavior for such a component has no local precedent.
- No measurements exist for the bundle cost of adding a UI package; the earlier notes explicitly say this was not measured ([repo-gap-audit.md:133](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md#L133)).

## 2. What presentation logic is deliberately kept out of core/vue, and why?

### Takeaway

The project identity is a headless composable layer: core and vue own Solana state, lifecycle, errors, and Kit integration; apps own labels, layout, theming, and user-facing decisions. This is explicit in the README, wallet guide, error guide, and in how the packages are built.

### Cited Findings

- README states "A built-in wallet modal. Apps should build their own selection UI with `useWallets()`" under not-yet-supported features, while describing a single public wallet flow through `useWallets()`/`useWallet()` ([README.md:67-72](/Users/mohsenpakfetrat/Development/vue-solana/README.md#L67)).
- The wallets guide lists "A built-in wallet modal or UI package" as not included, alongside server-side wallet prompts and private-key handling, and instructs apps to render unsupported-capability UI from `canSignMessage`, `canSignTransaction`, `canSignAllTransactions`, and `canSignAndSendTransaction` ([wallets.md:48-53](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/wallets.md#L48), [wallets.md:39-46](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/wallets.md#L39), [wallets.md:108-124](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/wallets.md#L108)).
- The error guide tells consumers: "Use stable `error.code` values for UI decisions. Keep `error.cause` for debugging and logs"; the stable code list is deliberately generic and app-facing ([errors.md:8-10](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/errors.md#L8), [errors.md:27-44](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/errors.md#L27)).
- `useExecution()` is documented as the shared supersede-and-report state machine behind every action composable, with one in-flight execution, derived `loading`, normalized `SolanaError`, and scope disposal; it deliberately exposes state, not markup ([use-execution.ts:15-35](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/use-execution.ts#L15), [use-execution.ts:49-102](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/use-execution.ts#L49)).
- The only published component is intentionally logic-only: the provider exposes no UI and passes options into `provideSelectedWalletAccount()` ([SelectedWalletAccountProvider.ts:7-35](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/components/SelectedWalletAccountProvider.ts#L7)).
- Nuxt auto-imports composables and setup values but has no component registration path: the module calls `addImports()` only, never `addComponent()` ([module.ts:133-147](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/module.ts#L133), [imports.ts:1-105](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/imports.ts#L1)).
- The docs demo keeps presentation in the app: `DemoWalletPanel.vue` accepts already-formatted strings/colors and emits events ([DemoWalletPanel.vue:3-25](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoWalletPanel.vue#L3)); `ShowcaseApp.vue` uses app i18n and app-level `@nuxt/ui` components for labels/badges/icons ([ShowcaseApp.vue:14-60](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/content/ShowcaseApp.vue#L14)).
- The scanner demo explicitly avoids a packaged "pay button": scanned URLs are untrusted input, so the panel shows details and a wallet link and states "Never auto-send a scanned request" ([SolanaPayScannerPanel.vue:112-116](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L112), [SolanaPayScannerPanel.vue:225-229](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L225)).
- Prior strategy notes frame a wallet modal as a "strategic product pivot" versus the current "apps build their own selection UI" stance, and score it worst on maintainability because of UI/CSS/a11y/SSR/mobile ownership ([strategy-feasibility.md:109](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L109), [strategy-feasibility.md:135](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L135), [strategy-feasibility.md:149](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L149)).

### Inferences

- A UI package that ships text, colors, icons, or modal focus management would move responsibilities the repo currently delegates to apps; that is a policy change, not just an additive package.
- The safest extension of the repo's identity is slots/props/state with no copy or theme of its own, leaving the docs' i18n and `@nuxt/ui` styling in app land.

### Gaps

- There is no written statement forbidding a future UI package — only deferrals and "not included yet" language — so the decision is open but must be presented as changing the current product stance.

## 3. What hard constraints would a published `@vue-solana/ui` package hit?

### Takeaway

The workspace would auto-discover a fourth package, but nearly every packaging, bundle, docs, and CI guard is hard-coded to core/vue/nuxt. A UI package must either be added to those gates explicitly or it will ship without the protections the repo relies on.

### Cited Findings

- Workspace discovery is automatic via `packages/*`, and root scripts use `pnpm -r` for build/typecheck/clean, so a new package under `packages/ui` is picked up by recursive commands ([pnpm-workspace.yaml:1-4](/Users/mohsenpakfetrat/Development/vue-solana/pnpm-workspace.yaml#L1), [package.json:7-30](/Users/mohsenpakfetrat/Development/vue-solana/package.json#L7)).
- CI runs lint, format, test, typecheck, build, `size:packages`, `check:entries`, `check:esm-map`, `check:externals`, buffer declarations, `pack:size`, and e2e ([ci.yml:37-71](/Users/mohsenpakfetrat/Development/vue-solana/.github/workflows/ci.yml#L37)).
- ESM-only is enforced: `check-exports-map.mjs` requires `"type": "module"`, no top-level `main`, no `require` condition, `.d.ts` (not `.d.mts`) types, and a `files` exclusion for `.d.mts`; its default package list is exactly core/vue/nuxt ([check-exports-map.mjs:5-7](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-exports-map.mjs#L5), [check-exports-map.mjs:17-47](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-exports-map.mjs#L17)). All three current packages set `sideEffects: false` ([core/package.json:23-24](/Users/mohsenpakfetrat/Development/vue-solana/packages/core/package.json#L23), [vue/package.json:23-24](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/package.json#L23), [nuxt/package.json:22-23](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/package.json#L22)).
- `check-export-map.ts` also hard-codes core/vue/nuxt and requires each `exports` subpath to have a matching build entry; a new package must be added there or its `exports`/`entries` drift is unchecked ([check-export-map.ts:8-35](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-export-map.ts#L8), [check-export-map.ts:39-67](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-export-map.ts#L39)).
- `check-pack-size.mjs` hard-codes the same three packages and per-package byte budgets (core 50 KB, vue 80 KB, nuxt 20 KB) and rejects `.d.mts` in tarballs ([check-pack-size.mjs:5](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-pack-size.mjs#L5), [check-pack-size.mjs:33-48](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-pack-size.mjs#L33)). A UI package needs its own budget or the default 100 KB applies if added ([check-pack-size.mjs:34-35](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-pack-size.mjs#L34)).
- The standalone-install smoke matrix packs exactly core/vue/nuxt and typechecks consumer imports from their published tarballs; UI would need a consumer case to catch a broken exports map ([smoke-standalone-installs.mjs:123-133](/Users/mohsenpakfetrat/Development/vue-solana/scripts/smoke-standalone-installs.mjs#L123), [smoke-standalone-installs.mjs:166-180](/Users/mohsenpakfetrat/Development/vue-solana/scripts/smoke-standalone-installs.mjs#L166)).
- `check-lean-imports.mjs` only walks built entries of core and vue. It forbids static edges to mobile-wallet, buffer-polyfill, `@solana-mobile/`, `qrcode`, `jsqr`, and `buffer`, with a deliberate iOS-wallet/tweetnacl debt exemption for `vue/dist/index.mjs` only ([check-lean-imports.mjs:11-24](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-lean-imports.mjs#L11), [check-lean-imports.mjs:59-86](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-lean-imports.mjs#L59), [check-lean-imports.mjs:194-253](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-lean-imports.mjs#L194)). A UI package's eager graph is not currently gated at all.
- Bundle reporting also hard-codes core/vue/nuxt entry lists; Vue entries are measured from every built `.mjs` file, with dynamic imports excluded and report-only budgets ([report-bundle-sizes.mjs:15-32](/Users/mohsenpakfetrat/Development/vue-solana/scripts/report-bundle-sizes.mjs#L15), [report-bundle-sizes.mjs:67-100](/Users/mohsenpakfetrat/Development/vue-solana/scripts/report-bundle-sizes.mjs#L67)).
- Externals checks assert that Kit stays external in core's kit entry, core stays external in Vue's shared chunks, and Vue stays external in Nuxt's runtime plugin ([check-externals.ts:6-20](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-externals.ts#L6)). A UI package that bundles Vue, Kit, or `@vue-solana/core` would need a new externals entry to be caught.
- Root TypeScript path aliases enumerate only core/vue/nuxt ([tsconfig.base.json:7-14](/Users/mohsenpakfetrat/Development/vue-solana/tsconfig.base.json#L7)); root Vitest aliases are generated for core/vue and separately for nuxt runtime ([vitest.config.ts:24-48](/Users/mohsenpakfetrat/Development/vue-solana/vitest.config.ts#L24)). Tests live under `packages/**/*.test.ts` so new package tests are included, but imports of `@vue-solana/ui/*` need aliases if app/docs tests use them ([vitest.config.ts:50-57](/Users/mohsenpakfetrat/Development/vue-solana/vitest.config.ts#L50)).
- Vue's release build already batches declaration rollup in groups of nine because a single pass needs more than 8 GB; adding many component entries increases CI build pressure ([build.release.config.ts:11-17](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/build.release.config.ts#L11)).
- Nuxt auto-import sources must be real built files, not package subpaths, because generated `.d.ts` relative specifiers bypass the `exports` map; registering `from` via the module's resolved `vueDist` fixed silent `any` degradation ([imports.ts:74-115](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/imports.ts#L74)). Component auto-registration would require new module code; today the module only has `solanaAutoImports()` and `solanaSetupAutoImports()` lists ([imports.ts:3-66](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/imports.ts#L3)).
- SSR boundaries are strict: Nuxt registers a client plugin and a separate server plugin, with the server context deliberately inert for wallet/RPC work ([module.ts:125-147](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/module.ts#L125), [server-plugin.ts:14-43](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/src/runtime/server-plugin.ts#L14)); troubleshooting docs say composables are SSR-safe but real RPC/wallet work must run after hydration ([troubleshooting.md:50](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/troubleshooting.md#L50)); the Nuxt scanner is wrapped in `<ClientOnly>` ([examples/nuxt/app/app.vue:32-39](/Users/mohsenpakfetrat/Development/vue-solana/examples/nuxt/app/app.vue#L32)); docs `/demo` is `ssr: false` in all seven locales ([nuxt.config.ts:139-145](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/nuxt.config.ts#L139)).
- Any new docs page must be mirrored structurally in all locale trees: `locale-docs.test.ts` fails on missing/stale files, heading level/order drift, and code-fence count drift ([locale-docs.test.ts:6-13](/Users/mohsenpakfetrat/Development/vue-solana/packages/core/src/locale-docs.test.ts#L6), [locale-docs.test.ts:85-120](/Users/mohsenpakfetrat/Development/vue-solana/packages/core/src/locale-docs.test.ts#L85)); AGENTS requires translated changes in the same change set ([AGENTS.md:250-254](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L250)).
- The docs app is the minimal-install, published-version demo: it depends only on `@vue-solana/nuxt` at an exact published version, and tests reject ranges or `workspace:*` ([docs-import-policy.test.ts:6-19](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/docs-import-policy.test.ts#L6), [docs-package-policy.test.ts:16-41](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/docs-package-policy.test.ts#L16), [apps/docs/package.json:16-30](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/package.json#L16)). A UI package cannot be demonstrated in docs until it is published and the pin is bumped.
- Bundle invariants are explicit: core's root barrel must not re-export `buffer-polyfill`, `ios-wallet`, or `mobile-wallet`; the first adds ~27 KB Buffer polyfill, the latter add tweetnacl (~32 KB) and MWA (~98 KB) to every consumer ([AGENTS.md:182-192](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L182)). `qrcode`/`jsqr` are already kept behind lazy/dynamic paths ([check-lean-imports.mjs:65-77](/Users/mohsenpakfetrat/Development/vue-solana/scripts/check-lean-imports.mjs#L65), [useSolanaQrScanner.ts:53-68](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaQrScanner.ts#L53)).

### Inferences

- A new package is mechanically easy to create but expensive to make a first-class citizen: at minimum add it to the export-map check, ESM-map defaults, pack-size budgets, standalone smoke matrix, bundle report/lean checks, externals checks, TS aliases if docs/tests import it, Nuxt module imports if auto-imports are wanted, release changesets, and locale docs.
- Publishing a root barrel that re-exports `@vue-solana/vue` would inherit the Kit mirror (~117 KB) and the known iOS/tweetnacl eager debt (~38.9 KB of a 67.4 KB Vue eager chunk), so a UI package should use narrow subpath imports and avoid root re-exports of the whole Solana surface ([AGENTS.md:188-192](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L188)).
- SSR-safe components must render from injected headless state without touching camera, wallet discovery, clipboard, or storage until mounted/client-side; the existing guards show the intended shape.

### Gaps

- No local policy defines a tarball or eager-chunk budget specifically for UI components.
- No existing CI job checks accessibility, visual regression, CSS output, or icon assets; those would be new gates if styled components ship.

## 4. Would a UI package need new runtime npm dependencies? Which are forbidden or risky?

### Takeaway

A headless/slot-based package needs no new runtime dependency beyond `vue` and `@vue-solana/vue`; anything styled, icon-bearing, or using a headless-UI library would add a new dependency and versioning surface. The forbidden list targets duplicate Solana/Kit stacks and React wallet UI packages, not CSS utilities, but lean-bundle rules would still punish static heavy imports.

### Cited Findings

- Current published runtime dependencies are minimal: core has Kit, Wallet Standard, MWA, `qrcode`, and `tweetnacl` with `buffer` as an optional peer; vue depends only on `@vue-solana/core` and `jsqr` with `vue` as a peer; nuxt depends only on core and vue with `nuxt` as a peer ([core/package.json:128-152](/Users/mohsenpakfetrat/Development/vue-solana/packages/core/package.json#L128), [vue/package.json:223-229](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/package.json#L223), [nuxt/package.json:58-64](/Users/mohsenpakfetrat/Development/vue-solana/packages/nuxt/package.json#L58)).

- React-specific Wallet Standard packages (`@wallet-standard/react`, `@wallet-standard/ui`, `@wallet-standard/ui-registry`) are explicitly forbidden; only `@wallet-standard/app`, `/base`, and `/features` are allowed ([AGENTS.md:314](/Users/mohsenpakfetrat/Development/vue-solana/AGENTS.md#L314)).

### Inferences

- A `@vue-solana/ui` package should declare `vue` and `@vue-solana/vue` as peers/dependencies and re-use `useWallet`, `useWallets`, `useSignIn`, `useSolanaPay`, `useSolanaQrCode`, and `useSolanaQrScanner` rather than adding a wallet SDK, QR library, or chain client of its own.
- Tailwind/`@nuxt/ui` are not forbidden, but making them runtime requirements would invert the current layering (apps choose their design system) and add consumer configuration; using CSS variables and plain class hooks is the lower-risk option.
- Iconify/`UIcon` usage is app-level here; shipping an icon set adds a dependency and licensing/bundle question with no local precedent.
- Headless UI/a11y libraries (dialog/listbox primitives) are not explicitly banned, but they are a new dependency whose API version would sit under the UI package's own release cadence; if used, they should be peer deps or isolated behind an opt-in styled subpath, not in the headless core.
- `@solana/kit-plugin-wallet`, `gill`, `@solana/wallet-adapter-*` React UI, or anything pulling `@solana/web3.js` should be treated as forbidden or high-risk under the current policy even if a UI package seems like a natural place for them.

### Gaps

- No local evaluation exists of a specific Vue headless-UI library (e.g., Reka UI/Radix Vue) or icon set, so compatibility and bundle cost are unknown.
- No local decision exists on whether CSS should be injected at runtime, shipped as a static file consumers import, or avoided entirely.

## 5. What is the smallest realistic product boundary that preserves the repo's identity?

### Takeaway

The smallest defensible product is an **opt-in, unstyled, slot-driven wallet-connect/payment-display layer built on existing composables**; a full styled modal or broad component catalog is a separate product bet that conflicts with the documented "apps own selection UI" stance.

### Cited Findings

- The roadmap places "Wallet Modal Or UI Package" under "Later — large API or architecture commitments" and describes it as "prebuilt connect and sign flows", not a current priority ([roadmap.md:14-21](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/roadmap.md#L14), [roadmap.md:45-47](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/roadmap.md#L45)).
- README and wallets guide both say apps should build their own wallet selection UI and that a built-in modal is not included ([README.md:67-72](/Users/mohsenpakfetrat/Development/vue-solana/README.md#L67), [wallets.md:48-53](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/wallets.md#L48)).
- The prior report explicitly defers a history component or wallet modal and recommends a composable-only first slice ([Next Vue Solana feature.md:52](/Users/mohsenpakfetrat/Development/vue-solana/reports/Next%20Vue%20Solana%20feature.md#L52), [strategy-feasibility.md:167-189](/Users/mohsenpakfetrat/Development/vue-solana/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md#L167)).
- The docs demo proves the minimal split works: behavior lives in `useDemoWallet()` ([useDemoWallet.ts:5-120](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/composables/demo/useDemoWallet.ts#L5)) and presentation in a props/emit SFC with slots handled by `DemoPanel` ([DemoWalletPanel.vue:3-59](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/demo/DemoWalletPanel.vue#L3)).
- `SelectedWalletAccountProvider` is a precedent for shipping logic-only components that render only `slots.default?.()` ([SelectedWalletAccountProvider.ts:17-35](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/components/SelectedWalletAccountProvider.ts#L17)).
- Capability gating and translated status/copy are already app-level concerns, so a component that owns them would need either i18n integration or slot-provided labels ([wallets.md:108-124](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/content/guides/wallets.md#L108), [useDemoWallet.ts:12-37](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/composables/demo/useDemoWallet.ts#L12), [ShowcaseApp.vue:1-14](/Users/mohsenpakfetrat/Development/vue-solana/apps/docs/app/components/content/ShowcaseApp.vue#L1)).
- Solana Pay's safest packaged surface is already headless: build/parse + QR + polling exist, and the example scanner deliberately provides no send path ([useSolanaPay.ts:20-109](/Users/mohsenpakfetrat/Development/vue-solana/packages/vue/src/composables/useSolanaPay.ts#L20), [SolanaPayScannerPanel.vue:112-116](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L112), [SolanaPayScannerPanel.vue:214-229](/Users/mohsenpakfetrat/Development/vue-solana/examples/vue-vite/src/components/panels/SolanaPayScannerPanel.vue#L214)).

### Inferences

- Recommended boundary, in order of increasing commitment:
  1. **No new package yet:** add one or two headless helpers to `@vue-solana/vue` that package the repeated view-model logic already in `useDemoWallet`/`WalletPanel` (formatted status, enablement, normalized error text), and keep the existing panels as the reference UI. This preserves the current identity exactly.
  2. **If a package is required:** `@vue-solana/ui` should ship only unstyled, slot-based `WalletList`/`ConnectButton` and `PaymentRequestDisplay`/`QrScannerFrame`-style components (names illustrative), with no CSS framework, no bundled icon set, no wallet icons licensing, no strings, no modal focus policy, and no transaction sending. Every label, empty state, and error message comes from props/slots; all state comes from the existing composables.
  3. **Styled theme is separate:** any `@nuxt/ui`/Tailwind-flavored theme should live in the docs app or a separately versioned theme package, so the core UI package does not inherit app design tokens or locale-copy maintenance.
- Explicit non-goals for the smallest slice: no wallet modal overlay, no transaction builder/send button, no token/portfolio dashboard, no program-specific display, no key/seed handling, no server-side wallet prompts, no QR auto-send, no auto-retry, and no new Solana SDK.
- To stay inside the gates, each component needs its own ESM subpath export and build entry, `sideEffects: false`, `.d.ts` types with `.d.mts` excluded, no static heavy deps, client-only behavior gated by lifecycle hooks, and a Nuxt module change only if auto-registration is explicitly desired.

### Gaps

- The maintainer has not chosen between "headless helper in `@vue-solana/vue`" and a fourth published package; both fit the evidence, but only the first avoids a new versioning surface.
- No local design system, icon license, or accessibility baseline exists to copy, so any styled layer would be a genuine new product decision.
