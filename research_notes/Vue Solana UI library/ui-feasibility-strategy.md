# Vue Solana UI library feasibility and strategy

Scope: decision research only; no files other than this note were changed. Research date 2026-11-25. Local repository state inspected directly: packages at `4.5.1`, root barrel exports no CSS/style/component subpaths, and transaction history is already implemented and archived ([core package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json), [vue package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json), [nuxt package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/package.json), [local git log and package inspection, 2026-11-25](https://github.com/vue-solana/vue-solana)).

Assumptions behind all estimates below: (1) Vue Solana remains a headless, Kit-first library whose differentiator is reactive state over Kit, not visual design; (2) no funded design/accessibility owner exists yet; (3) “user value” means first-time wallet onboarding and daily dapp work, not npm downloads, which include CI/transitive installs ([competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md)); (4) cost scores are comparative engineering estimates grounded in the cited repo obligations, not measured person-days; (5) web search was unavailable (HTTP 402), so public evidence is limited to primary pages fetched directly and the earlier primary-source research notes ([websearch attempt, 2026-11-25](https://www.w3.org/), [competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md)).

## Key question 1: What are the candidate UI features, from smallest to largest, and how do they score?

### Takeaway

Order candidates by the surface they own: a QR scanner wrapper and a status badge are small; a connect button is small-to-medium; wallet picker/account menu, activity feed, token amount input, and a full design system grow quickly in visual, accessibility, and protocol obligations. On the repo’s own constraints, no UI component scores as well as staying headless; the best candidate slice is a docs-only copy-paste recipe set, and the best eventual package would be unstyled components, never a design system ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).

### Cited Findings

Scoring: value /5 (higher is better), cheapness /5 (5 = small build), low maintenance /5 (5 = low tail), architecture safety /5 (5 = fits ESM/lean/SSR/headless constraints). Total /20. Scores are my judgment from the cited evidence, not measured metrics.

- The earlier feasibility rubric scored “wallet modal / built-in UI package” **54/100**, behind transaction history (87), priority fees (82), diagnostics (76), server RPC docs (77), and most other candidates, specifically because of the CSS/a11y/SSR/mobile matrix and a second versioning surface ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).
- The public roadmap places wallet modal/UI under “Later” as a large API or architecture commitment, alongside Anchor helpers, desktop native wallets, RPC failover, and advanced indexing ([roadmap.md](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/roadmap.md)).
- The repo currently documents “no built-in wallet modal; apps should build their own selection UI with `useWallets()`” in README, knowledge bundle, skill file, and docs guide, so a UI package is a stance change, not an incremental API addition ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [knowledge-bundle/guides/wallets.md](https://github.com/vue-solana/vue-solana/blob/main/knowledge-bundle/guides/wallets.md), [skills/vue-solana/SKILL.md](https://github.com/vue-solana/vue-solana/blob/main/skills/vue-solana/SKILL.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).
- A prior repo audit describes the state layer as intentionally headless and says a wallet modal/UX layer is viable only as an opt-in subpath or package, because root bundles are size-sensitive ([repo-gap-audit.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md), [core index.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts)).
- The only Vue component shipped by the Vue package is a renderless provider (`SelectedWalletAccountProvider`) that calls `provideSelectedWalletAccount()` and renders a slot; it is not a visual component ([SelectedWalletAccountProvider.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts)).
- Large UI download numbers do not prove product fit: `@solana/wallet-adapter-react-ui` had ~951,660 monthly downloads but still peer-depends on legacy `@solana/web3.js ^1.99.0`, while the maintained Kit path moved to Wallet Standard and React-specific UI packages ([competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md), [react-ui npm metadata](https://registry.npmjs.org/@solana/wallet-adapter-react-ui/latest)).
- A full-stacked UI toolkit illustrates the scale gap: `@reown/appkit@2.0.0` is ESM with separate `./vue`, `./react`, `./vue-core`, and `./library/vue` entries, ~1 MB unpacked, and six internal UI/controller dependencies (`@reown/appkit-ui`, `@reown/appkit-scaffold-ui`, `@reown/appkit-controllers`, etc.) — it is multi-chain/Ethereum-oriented, so it is a scale reference, not a Solana competitor ([npm registry](https://registry.npmjs.org/@reown/appkit/latest)).

### Inferences

- The candidate ranking favors thin wrappers over existing composables and rejects anything that owns a design language. A connect button with slots plus a status badge are the only components that could be added without importing a visual contract.
- A wallet modal has the strongest apparent demand but the worst risk-adjusted score: it is the one component where a11y, mobile handoff, and theming are unavoidable, and the repo has already spent many releases on the underlying wallet behavior ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).
- An activity feed UI is unusually cheap **because history already shipped**; it is the natural first consumer of the prior recommendation, but it does not justify creating a package by itself.
- A full design system would contradict the package’s ESM/lean-import discipline: all three packages currently expose exact JS/type subpaths and no CSS/style/component export ([core package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json), [vue package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json), [nuxt package.json](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/package.json), [local export inspection](https://github.com/vue-solana/vue-solana)).

### Gaps

- No issue, discussion, interview, or usage-telemetry corpus quantifies demand for any specific component; the earlier report found zero repository issues and disabled Discussions, so all “value” scores remain judgment under uncertainty ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).
- No implementation benchmark exists for a concrete component package; the cost estimates are derived from existing examples and test surfaces, not from a prototype.
- Public web search failed with HTTP 402, so no 2026 blog/community sentiment data was gathered; npm/GitHub primary metadata came from the earlier competitor notes ([competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md)).

## Key question 2: What obligations come with a styled component package, and which can be avoided in v1?

### Takeaway

A styled package inherits a contract for CSS delivery, tokens/dark mode, keyboard and screen-reader behavior, SSR/hydration, mobile handoff, i18n, release synchronization, translated docs, and visual baselines. Almost all of that is avoidable in a v1 that ships **unstyled, slot-based components with no modal, no toast manager, no embedded strings, and no CSS file**; the obligations return the moment the package claims visual polish ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [locale-docs.test.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/locale-docs.test.ts)).

### Cited Findings

- ESM-only publishing, `sideEffects: false`, exact `types`/`import` subpaths, `.d.mts` tarball exclusions, and standalone-install smoke tests are existing hard gates that a new package must join ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).
- The clean precedent for a “component” in this repo is renderless: the selected-wallet-account provider only provides context and returns a slot ([SelectedWalletAccountProvider.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts)).
- The example wallet panel already implements its own status pill, disabled states, notices, copy-address action, and error formatting from composables — evidence that the state contract is reusable while the visual contract is app-specific ([WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/WalletPanel.vue)).
- Docs and examples already house hand-written UI: the Nuxt scanner is wrapped in `<ClientOnly>` and the Solana Pay scanner panel has its own scoped styles ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [DemoPayScannerPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/app/components/demo/DemoPayScannerPanel.vue)).
- If visual parity is promised, accessibility is not optional: the W3C modal pattern explicitly warns that marking a dialog `aria-modal` while other users can still interact with background content has severe negative ramifications for assistive-technology users ([W3C ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

### Inferences

- The avoidable-vs-unavoidable line is simple: **presentation is avoidable in v1; interaction semantics are not.** If the package only renders buttons/lists with consumer-supplied classes and labels, it can defer CSS, tokens, dark mode, i18n, deep-link handoff, and screenshots.
- Anything called a “modal,” “toast system,” or “styled button” crosses the line: it owns focus management, strings, and a look that must stay stable, and it would need real wallet testing on Android/iOS/desktop before release.
- Docs-only recipes avoid the fourth version surface and keep the public stance (“apps own UI”) intact while still reducing the copy-paste burden that motivates a UI package ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).
- If a package is eventually created, an unstyled component package is still the right v1 shape; a styled design system should be a separate product decision with its own owner.

### Gaps

- No measurement of how much app-side wallet-panel code is duplicated across real consumers was available; the two example panels show a pattern but are maintained together in one repo ([WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/WalletPanel.vue), [Nuxt WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/nuxt/app/components/WalletPanel.vue)).
- No dark-mode/token contract or visual baseline exists in the packages today, so the amount of CSS API work is estimated, not measured ([package export inspection](https://github.com/vue-solana/vue-solana)).
- No real-wallet accessibility audit was found; the W3C APG requirements are normative guidance, not evidence that a proposed component would pass an audit ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

## Key question 3: How does this compare with the earlier read-only transaction-history API recommendation, and can a history UI be a later consumer?

### Takeaway

The earlier report recommended a read-only history API precisely to avoid UI ownership, and that API has now shipped and been archived; a history UI is therefore a **later consumer of a stable data contract**, not a reason to pivot the library toward components now ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md), [plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md)).

### Cited Findings

- The earlier report chose `getTransactionHistory()` / `useTransactionHistory()` / `useSolanaTransactionHistory()` because it closes simulate → sign/send → confirm → inspect without a new package, dependency, heavy static edge, wallet-protocol change, or Nuxt secret-boundary change ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md), [strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).
- The same report explicitly deferred “a history component” and a wallet modal, and scored the combined “headless wallet picker / UI package” eighth of nine ranked candidates ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).
- The implementation plan is archived with all boxes checked: core `getTransactionHistory()`, Vue `useTransactionHistory()` with `items`/`hasMore`/`refresh`/`loadMore`, Nuxt alias, docs section, example panels, and tests ([plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md)).
- Current exports confirm the shipped state: `packages/vue/src/index.ts` re-exports `useTransactionHistory`, `packages/nuxt/src/imports.ts` maps it to `useSolanaTransactionHistory`, and both examples mount a `TransactionHistoryPanel` ([Vue index.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts), [Nuxt imports.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts), [Vue panel](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransactionHistoryPanel.vue), [Nuxt panel](https://github.com/vue-solana/vue-solana/blob/main/examples/nuxt/app/components/TransactionHistoryPanel.vue)).
- The e2e suite includes “lists transaction history and appends older pages,” and the example panel displays signature, slot, success/failure, loading, and error state from the composable without decoding instructions ([e2e/example-apps.spec.ts](https://github.com/vue-solana/vue-solana/blob/main/e2e/example-apps.spec.ts), [TransactionHistoryPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransactionHistoryPanel.vue)).
- The archived plan deliberately forbade decoded/interpreted rows, explorer presets, persistence, retries, and a history component; those limits are what keep history a stable upstream contract ([plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md)).
- The earlier report’s conclusion was that the next advantage is owning “the state between network events and the user,” and that a later diagnostics view could join signatures, simulation logs, and normalized errors without reopening client architecture ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).

### Inferences

- Because the data layer is now stable and exercised in e2e, a later history-list component can be a thin, replaceable consumer: pass an address source into `useTransactionHistory()`, render `items`, and expose refresh/load-more events. That is a component recipe today and a candidate package component later.
- Adding a UI package now would not contradict the history recommendation at the data level, but it would reopen exactly the maintenance frontier (CSS/a11y/i18n/SSR/mobile/release surface) that the history recommendation deliberately avoided ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).
- A history UI is the safest future package component precisely because it is read-only and has no wallet/deep-link semantics; the riskiest future component remains the wallet picker modal.
- Don’t add “human readable” transaction categorization to a UI recipe: the archived plan excluded decoding to avoid turning a read helper into an indexer/program catalog ([plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md)).

### Gaps

- No evidence was found that end users actually want a prebuilt activity-feed component versus the existing composable plus app styling; the examples demonstrate feasibility, not demand ([TransactionHistoryPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransactionHistoryPanel.vue), [reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).
- No design contract exists for “transaction row,” including how to display failures, memos, block time, and explorer links; those fields are available in the result type but intentionally uninterpreted ([plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md)).

## Key question 4: What exit criteria or trigger conditions justify a UI package later?

### Takeaway

Publish UI only when duplication is proven at the **DOM/CSS/interaction** level, the composable APIs have been stable for at least one release, a named owner exists for a11y/theming/i18n, and mobile handoff has been validated with real wallets. Until then, repeated requests for headless behavior should be answered with composables and examples, not a package ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).

### Cited Findings

- No demand signal currently clears that bar: the earlier report found zero repository issues, Discussions disabled, and no accessible Reddit/Discord or interview corpus; npm downloads cannot distinguish humans from CI or explain retention ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md), [community-demand notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/community-demand.md)).
- The docs currently state that apps build their own wallet-selection UI, so changing that stance should require explicit, repeated user evidence rather than maintainer intuition ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).
- The repo has hard gates that a UI package must satisfy: `format`, `lint`, `test`, `typecheck`, `build:packages`, `build:examples`, docs build, standalone-install smoke, e2e, export-map checks, lean-import checks, and locale-structure tests ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [root package.json](https://github.com/vue-solana/vue-solana/blob/main/package.json)).
- Mobile wallet behavior is a mature but delicate area with MWA session fixes, iOS deep links/callbacks, wallet exclusivity, and signature verification recorded as hard-won behavior; a UI layer must not regress it ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [wallet-registry.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts)).
- The workspace allows examples to use unreleased packages while `apps/docs` pins published versions, which gives a place to prove a component in two apps before publishing it ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).
- W3C modal guidance defines the interaction contract a future picker would have to meet, including focus placement, Escape-to-close, focus return, and correct `aria-modal` usage ([W3C ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

### Inferences

Proposed exit criteria, all of which should be met before a published package:

1. **Demand:** at least three unsolicited requests for the same visual component, or two independent apps (one external) maintaining materially identical wallet-list/status markup that a shared component could replace. Existing issues/Discussions provide none today ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).
2. **Proven duplication:** the same component shape has been implemented in both example apps and validated in docs/demo, with a written list of shared class hooks/events; composable reuse alone does not count ([WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/WalletPanel.vue), [Nuxt WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/nuxt/app/components/WalletPanel.vue)).
3. **Stable contract:** underlying composables (`useWallets`, `useWallet`, `useSelectedWalletAccount`, `useTransactionHistory`, `useSignatureStatus`) have not changed shape for one full release, so the UI package does not chase API churn ([Nuxt imports.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts), [Vue index.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)).
4. **Owner and budget:** a named maintainer accepts CSS tokens, dark mode, keyboard/focus tests, translated docs strings, and visual baselines as ongoing work; otherwise the package inherits unowned obligations ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [locale-docs.test.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/locale-docs.test.ts), [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)).
5. **Mobile validation:** any connect/picker component has been exercised through real Android MWA, iOS browser wallet, and desktop Wallet Standard flows, including handoff/approval quirks recorded in the wallet guide ([wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).
6. **CI fits:** the new package passes the same export, smoke, size, SSR, and locale gates without adding React UI deps, a second Kit copy, or a heavy static edge ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).

### Gaps

- No threshold in the sources says how many requests justify a package; “three requests / two independent apps” is my proposed policy, not an observed rule ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).
- No process exists yet for collecting component requests, since Discussions are disabled and there are no repository issues; a simple “UI recipes” feedback link in docs would be needed to make the demand trigger measurable ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md)).

## Key question 5: What is the concrete v1 scope if a UI package is chosen, and what is the fallback scope if it is not?

### Takeaway

Recommended answer to the user’s question (“maybe a UI library?”): **not yet**. Do headless composables plus docs-only component recipes now, centered on wallet connection and the already-shipped history/status APIs. If a package is mandated anyway, make it an unstyled, opt-in `@vue-solana/ui` with two slot-based components and non-goals that explicitly exclude CSS, modals, i18n, and mobile-handoff guarantees ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md), [AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).

### Cited Findings

- The recommended fallback keeps the library’s current product boundary: “state-only composables, apps own selection UI,” which is already documented in README, knowledge bundle, skill file, and wallets guide ([README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [knowledge-bundle/guides/wallets.md](https://github.com/vue-solana/vue-solana/blob/main/knowledge-bundle/guides/wallets.md), [skills/vue-solana/SKILL.md](https://github.com/vue-solana/vue-solana/blob/main/skills/vue-solana/SKILL.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).
- The fallback still answers “what do I render?” with copyable code, which is the part of UI work that most reduces first-run friction without taking ownership of the user’s design system ([WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/WalletPanel.vue), [TransactionHistoryPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransactionHistoryPanel.vue)).
- The package variant deliberately looks like the existing renderless provider precedent and avoids the obligations that the W3C modal pattern and Playwright snapshot workflow would impose ([SelectedWalletAccountProvider.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts), [W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)).
- Publishing either way should be gated by the repo’s full CI matrix and locale doc structure test ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [root package.json](https://github.com/vue-solana/vue-solana/blob/main/package.json)).

### Inferences

- The final recommendation is: **no UI package in this release; ship docs-only recipes and keep the history/status APIs as the data contract.** Revisit the package only when the exit criteria are met. This answers “maybe a UI library?” with a clear no-now/yes-later decision rather than a menu of options.
- If the maintainer’s goal is differentiation, the higher-leverage queue from the earlier research remains fee helpers, diagnostics, token actions, and bundle performance rather than visual components ([reports/Next Vue Solana feature.md](https://github.com/vue-solana/vue-solana/blob/main/reports/Next%20Vue%20Solana%20feature.md), [competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md), [roadmap](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/roadmap.md)).
- If a future UI package ever ships, its first real component should be the read-only activity list, then connect button, then wallet picker last, following the risk ordering established here and the fact that history is already stable ([plans/archived/transaction-history.md](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md), [W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

### Gaps

- No design/design-system stakeholder was interviewed, so the recommendation assumes visual ownership is not currently available; if it is, the styled-package option becomes more attractive but still needs demand evidence ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)).
- No prototype or bundle measurement was produced for `@vue-solana/ui`; the “depends only on vue + existing packages” claim is an architectural constraint for v1, not a measured result.
- The exact wording/locale placement of new docs recipes needs translator review; only structural mirroring is enforced by the current test ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md), [locale-docs.test.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/locale-docs.test.ts)).
