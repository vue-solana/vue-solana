# Current Vue Solana public surface and concrete capability gaps (repo audit, 2026-11-21)

## What can developers already do with `@vue-solana/core`, `@vue-solana/vue`, and `@vue-solana/nuxt`?

### Takeaway

As shipped at version `4.3.0`, the three packages form a Kit-first stack in which core supplies framework-agnostic clients/helpers, Vue supplies reactive composables and wallet/transaction state, and Nuxt supplies auto-imports plus a client/server plugin boundary ([packages/core/package.json:1-4](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json), [packages/vue/package.json:1-4](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json), [packages/nuxt/package.json:1-4](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/package.json)). The differentiator is already the Vue/Nuxt lifecycle, wallet, and reactive workflow layer rather than a replacement for Kit itself, because every package deliberately re-exports the full `@solana/kit` surface and the docs tell app code to build messages with Kit helpers plus a program client ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)).

### Cited Findings

- **Audit scope.** This audit uses only the current working tree as of the supplied date, 2026-11-21; it deliberately does not read or rely on `/plans/**`, so conclusions are derived from shipped source, manifests, public docs, examples, and tests rather than internal planning material.
- **Public entry points are intentionally narrow at the package-root level and broad through subpaths.** Core exposes 16 subpaths including `address`, `action`, `buffer-polyfill`, `types`, `clusters`, `errors`, `ios-wallet`, `kit`, `mobile-wallet`, `rpc`, `timeout`, `transaction`, `wallet`, `wallet-standard`, `token-accounts`, and three Solana Pay entries ([packages/core/package.json:27-108](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json)). Vue exposes a root barrel plus one subpath per composable/SWR/Kit/buffer-polyfill ([packages/vue/package.json:27-204](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json)). Nuxt exposes only `.`, `./buffer-polyfill`, `./kit`, and `./server`; its real breadth is the auto-import map ([packages/nuxt/package.json:26-43](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/package.json), [packages/nuxt/src/imports.ts:3-44](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts)).
- **Core root barrel intentionally omits heavy optional paths.** It exports the general primitives and Solana Pay modules, but not `buffer-polyfill`, `ios-wallet`, or `mobile-wallet`, with explicit bundle-size comments ([packages/core/src/index.ts:1-15](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts), [packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts)). Clashing Kit names are resolved explicitly so the package's own `SolanaError`, error-code type, and transaction status win at the root, while Kit originals remain available through `/kit` ([packages/core/src/index.ts:36-57](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts); the same policy is applied in Vue at [packages/vue/src/index.ts:48-56](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)).
- **Core client setup is already substantial.** `createSolanaClient()` resolves cluster/HTTP/WebSocket endpoints, supports a Kit `payer` or a base64 Ed25519 `payerSecretKey`, and builds the client with the official RPC stack ([packages/core/src/kit.ts:100-124](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [packages/core/src/kit.ts:126-195](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts)). The default stack composes `solanaRpc()` plus `rpcAirdrop()`, and `solanaRpc()` installs planner/signing/sending capabilities; a client send requires `payer` ([apps/docs/content/packages/core.md:111](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/core.md), [apps/docs/content/guides/transactions.md:78-86](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)).
- **Core covers framework-agnostic transaction and token reads.** `signAndSendTransaction()` delegates to a wallet's sign-and-send feature or signs then submits through app RPC; `sendSignedTransaction()` submits bytes; `simulateTransaction()` returns normalized failure data plus logs/balances/loaded addresses; `confirmTransactionSignature()` polls `getSignatureStatuses` until a commitment is reached ([packages/core/src/transaction.ts:33-86](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [packages/core/src/transaction.ts:88-144](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [packages/core/src/transaction.ts:146-249](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts)). Token helpers read SPL Token and Token-2022 accounts, a single parsed token account, or a mint/owner balance using `jsonParsed` RPC data ([packages/core/src/token-accounts.ts:6-17](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/token-accounts.ts), [packages/core/src/token-accounts.ts:24-102](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/token-accounts.ts), [packages/core/src/token-accounts.ts:104-117](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/token-accounts.ts)).
- **Core has a real error and action vocabulary.** `SolanaError` carries a string code, message, cause, and optional wallet feature; codes cover wallet state, address, transaction timeout/not-found/failed, RPC, storage, input, capability, iOS redirect/decryption, and invalid signature cases ([packages/core/src/errors.ts:3-31](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [packages/core/src/errors.ts:38-52](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts)). `isSolanaError()` is structural across duplicate package copies, and `normalizeSolanaError()` preserves existing Solana errors and maps common rejection shapes to `USER_REJECTED` ([packages/core/src/errors.ts:77-97](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [packages/core/src/errors.ts:100-132](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts)).
- **Wallet support is broader than browser extensions.** The docs list Wallet Standard extensions, Android Mobile Wallet Adapter registered through Wallet Standard, and iOS universal-link wallets for Phantom/Solflare/Backpack in one discovery list ([apps/docs/content/guides/wallets.md:8-17](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:19-37](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Today the unified list can discover wallets, select without connecting, persist selected identity metadata, connect/disconnect, sign messages/transactions, and check capabilities through the `canSign*` flags ([apps/docs/content/guides/wallets.md:39-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:108-124](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Selecting/connecting is a state-only API: `useWallets()` returns `wallets`, `selectedWallet`, `refreshWallets`, and `selectWallet`, while `useWallet()` adds connect/disconnect, connection/capability refs, and `setWallet()` ([packages/vue/src/composables/useWallets.ts:3-12](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWallets.ts), [packages/vue/src/composables/useWallet.ts:6-24](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWallet.ts)).
- **Wallet behavior has non-trivial correctness work already implemented.** Connecting one wallet sweeps authorizations from every other discovered wallet, including uncached ones, with a two-second per-disconnect timeout; the sweep runs over discovery rather than only over cached adapters ([packages/vue/src/plugin/wallet-registry.ts:119-132](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts), [packages/vue/src/plugin/wallet-registry.ts:170-203](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts)). App-wide selected-account state supports filtering, `${walletName}:${address}` persistence, pending restore until wallets are discovered, and cross-tab `storage` sync ([packages/vue/src/composables/useSelectedWalletAccount.ts:20-52](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSelectedWalletAccount.ts), [packages/vue/src/composables/useSelectedWalletAccount.ts:82-193](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSelectedWalletAccount.ts)). The exported `SelectedWalletAccountProvider` is only a provider wrapper: its render function returns the default slot and it exposes no UI ([packages/vue/src/components/SelectedWalletAccountProvider.ts:7-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts)).
- **Vue composables cover the common dapp read/write surface.** The root barrel exports composables for account info, action state, airdrop, balance, client capability, planning/sending, program accounts, payer, request/subscription/tracked data, RPC, selected account, signing, SIWS, simulation, Solana Pay/QR, signature status, token accounts/balance, transaction state, wallet state, and Kit signer adapters ([packages/vue/src/index.ts:1-46](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)). The public docs enumerate the same list with short descriptions, including `useSendTransaction(s)` as the official Kit planner/sender wrapper that plans, signs, submits, and waits for `confirmed` commitment with no wallet popup ([apps/docs/content/packages/vue.md:123-206](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md)).
- **Vue read state is deliberately consistent but instance-local.** `useBalance`, `useAccountInfo`, `useProgramAccounts`, `useTokenAccounts`, and `useTokenBalance` share `useAddressRead`: empty input clears state, invalid input reports `INVALID_ADDRESS`, a newer refresh supersedes older results, an error drops data back to empty, and `refresh()` rethrows a normalized error ([packages/vue/src/composables/use-address-read.ts:21-37](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts), [packages/vue/src/composables/use-address-read.ts:44-102](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts)). The behavior is documented as intentional and is covered by tests such as stale-value clearing and out-of-order request protection ([apps/docs/content/guides/account-reads.md:143-173](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [packages/vue/src/composables/useAccountInfo.test.ts:99-145](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useAccountInfo.test.ts)).
- **Vue has a low-level live-data layer.** `useRequest()` accepts a function, a Kit request with `send()`, or a ref of either; it supports per-attempt abort signals and stale-while-revalidate state ([packages/vue/src/composables/useRequest.ts:26-47](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useRequest.ts), [packages/vue/src/composables/useRequest.ts:68-90](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useRequest.ts)). `useSubscription()` bridges a Kit reactive stream store and preserves stale data across reconnects ([packages/vue/src/composables/useSubscription.ts:31-81](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSubscription.ts), [packages/vue/src/composables/useSubscription.ts:95-149](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSubscription.ts)). `useTrackedData()` seeds from a one-shot RPC response and merges notifications with slot tracking ([packages/vue/src/composables/useTrackedData.ts:122-140](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useTrackedData.ts), [packages/vue/src/composables/useTrackedData.ts:167-240](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useTrackedData.ts)). SWR adapters add keyed cross-mount seeding to all three ([packages/vue/src/swr.ts:18-38](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts), [packages/vue/src/swr.ts:178-233](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts)).
- **Kit-compatible signer adapters are already shipped.** A wallet account can become a `MessageModifyingSigner` that preserves wallet-modified message bytes and invalidates stale signatures when the message changes ([packages/vue/src/composables/useWalletAccountMessageSigner.ts:16-45](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWalletAccountMessageSigner.ts), [packages/vue/src/composables/useWalletAccountMessageSigner.ts:52-103](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWalletAccountMessageSigner.ts)). A transaction signer exposes `modifyAndSignTransactions()` because a wallet may rewrite fee payer, priority fee, or guard instructions, and it re-derives the lifetime constraint if the wallet changes message bytes ([packages/vue/src/composables/useWalletAccountTransactionSigner.ts:27-56](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWalletAccountTransactionSigner.ts), [packages/vue/src/composables/useWalletAccountTransactionSigner.ts:65-140](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWalletAccountTransactionSigner.ts)). All wallet-account signers reject a connected account mismatch before signing ([packages/vue/src/composables/wallet-account-signer.ts:78-102](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/wallet-account-signer.ts)).
- **Batch signing and sending are implemented with explicit failure semantics.** `useSignTransactions()` prefers batch signing and falls back to legacy `signAllTransactions` ([packages/vue/src/composables/useSignTransactions.ts:12-29](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignTransactions.ts)). `useSignAndSendTransactions()` prefers a wallet batch feature, otherwise submits singular requests sequentially and throws `PartialSignAndSendError` with already-sent signatures so callers do not resubmit them ([packages/vue/src/composables/useSignAndSendTransactions.ts:20-89](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransactions.ts), [packages/core/src/errors.ts:54-67](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts)).
- **Solana Pay is implemented directly on Kit rather than wrapped from another package.** Core can encode/parse URLs and render QR codes, create references, poll non-verifying status, and verify settlement against expected recipient/amount/token ([apps/docs/content/guides/solana-pay.md:8-18](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md), [apps/docs/content/guides/solana-pay.md:142-172](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md)). The Vue composables cover request building, SVG QR, camera scanning with a lazy JS decoder fallback, and confirmation polling ([apps/docs/content/guides/solana-pay.md:59-80](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md), [apps/docs/content/guides/solana-pay.md:82-140](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md)).
- **Nuxt is the most opinionated of the three packages.** Its module auto-imports 40 composables plus SWR/context helpers under `useSolana*` aliases from concrete Vue files to avoid pulling the root barrel into SSR bundles ([packages/nuxt/src/imports.ts:3-44](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts), [packages/nuxt/src/imports.ts:88-104](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts)). `ModuleOptions` omits `wallet`, `payer`, and `payerSecretKey` and adds `clientPlugin?: boolean` for an app-installed client-only plugin ([packages/nuxt/src/module.ts:12-19](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts)). The browser plugin installs the Vue plugin and selected-account context; the server plugin creates a fresh, request-scoped, inert context with configured cluster/endpoints but no wallet discovery, RPC status check, or timers, and clears the module-level SWR cache before each render ([packages/nuxt/src/runtime/plugin.ts:10-24](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/plugin.ts), [packages/nuxt/src/runtime/server-plugin.ts:14-66](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts)). `@vue-solana/nuxt/server` provides read-only config/client creation and strips `payer`, `payerSecretKey`, and `wallet` at runtime ([packages/nuxt/src/runtime/server.ts:5-27](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server.ts)).
- **Examples and e2e confirm the main paths are exercised, not just typed.** Both example dashboards mount RPC status, balance, direct RPC, message signing, simulation, transfer, wallet, signer, live-data, and Solana Pay panels ([examples/vue-vite/src/App.vue:1-17](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/App.vue)). The Playwright suite covers dashboard/RPC load, wallet connect/restore/capability, signer message signing, submitted-vs-confirmed state, live request/subscription, tracked data, client payer funding and single/batch sends, SIWS, SWR remounts, simulation, Solana Pay request/QR/settlement, pasted URL validation, and mocked camera scanning ([e2e/example-apps.spec.ts:25-494](https://github.com/vue-solana/vue-solana/blob/main/e2e/example-apps.spec.ts)).
- **There are public-doc/implementation inconsistencies that matter for capability discovery.** The Vue and Nuxt package docs describe `useAccountInfo(address, { watch: true })` plus `stopWatching()` and say account info can subscribe to changes ([apps/docs/content/packages/vue.md:433-464](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [apps/docs/content/packages/nuxt.md:88](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)), but the implementation's options interface contains only `commitment`, its return has no `stopWatching()`, and its shared address-read helper only uses `onMounted`, a source `watch`, and manual `refresh()` ([packages/vue/src/composables/useAccountInfo.ts:8-23](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useAccountInfo.ts), [packages/vue/src/composables/use-address-read.ts:87-102](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts)). Similarly, docs say `useSignatureStatus()` can subscribe, but the implementation only calls `getSignatureStatuses` and schedules chained `setTimeout` polls ([apps/docs/content/packages/vue.md:188](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/src/composables/useSignatureStatus.ts:67-113](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignatureStatus.ts), [packages/vue/src/composables/useSignatureStatus.ts:158-205](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignatureStatus.ts)). The account-reads guide itself documents only `commitment` for `useAccountInfo()` ([apps/docs/content/guides/account-reads.md:62-78](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md)).

### Inferences

- The public surface is already broad enough for a developer to configure clusters, read common state, connect multiple wallet classes, sign/send/confirm transactions, use Kit signers, track live RPC data, and build Solana Pay flows without installing `@solana/kit` separately; the Kit mirror and subpath exports are the explicit design choice enabling that ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [apps/docs/content/packages/vue.md:169](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md)).
- The library's unique work is not the individual RPC call but the state machines around it: supersederacing reads, wallet exclusivity, capability errors, Kit signer adapters, SWR seeding, and Nuxt request isolation ([packages/vue/src/composables/use-address-read.ts:21-37](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts), [packages/vue/src/plugin/wallet-registry.ts:170-203](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts), [packages/vue/src/swr.ts:18-38](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts), [packages/nuxt/src/runtime/server-plugin.ts:46-66](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts)).
- The docs contradictions should be treated as a documentation-quality defect first; they also reveal a real product gap because users who believe `watch: true` exists have no shipped live-account convenience API to fall back to ([apps/docs/content/packages/vue.md:433-464](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/src/composables/useAccountInfo.ts:8-23](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useAccountInfo.ts)).
- Nuxt has the strongest SSR story of the three packages but still stops at "safe inert context plus manual server route pattern" rather than an integrated data-fetching primitive ([packages/nuxt/src/runtime/server-plugin.ts:14-43](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts), [apps/docs/content/packages/nuxt.md:180-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)).

### Gaps

- No usage telemetry, npm download breakdown, or issue-tracker data was reviewed, so this audit cannot say which shipped capabilities are most used.
- No `/plans/**` file was consulted, by instruction; alignment with internal roadmaps is therefore outside this audit.
- The audit cannot determine whether the stale `watch: true` / "subscribe" documentation is a leftover from an older API or an aspirational description, because no changelog history was consulted.
- No bundle-size measurements were taken for the existing exports; the audit relies on the explicit bundle comments in the source for heavy optional modules ([packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts)).

## Where are the concrete library-level gaps in account reads, transaction reliability, tokens, wallets, SSR, live data, program interaction, and errors?

### Takeaway

The main gaps are last-mile abstractions rather than missing Solana primitives: users still hand-wire raw Kit sources into Vue reactivity, assemble reliable transaction lifecycle UI themselves, build wallet pickers from state-only composables, and decode program data manually ([examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue), [apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [packages/vue/src/composables/useProgramAccounts.ts:35-84](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts)). Token operations, program-specific decoding, and desktop native wallet adapters are either absent or intentionally delegated to external program clients/packages, so they should be framed as opt-in integrations rather than core responsibilities ([apps/docs/content/packages/core.md:234](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/core.md), [apps/docs/content/guides/wallets.md:29-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).

### Cited Findings

- **Account fetching/decoding — implemented but low-level.** `useAccountInfo()` normalizes only the account envelope (`executable`, `lamports`, `owner`, `space`, `data: Uint8Array`) and accepts only `commitment`; there is no account decoder, codec registry, or multi-account read in that API ([packages/vue/src/composables/useAccountInfo.ts:8-23](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useAccountInfo.ts), [packages/vue/src/composables/useAccountInfo.ts:27-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useAccountInfo.ts)). `useProgramAccounts()` passes through `dataSize`/`memcmp` filters and `dataSlice`, decodes account data to bytes, and has no pagination/cursor option or typed decode hook ([packages/vue/src/composables/useProgramAccounts.ts:8-33](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts), [packages/vue/src/composables/useProgramAccounts.ts:56-84](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts)). The docs explicitly warn that program scans can be expensive and recommend filters, slices, caching, pagination, indexing, or dedicated RPC infrastructure ([apps/docs/content/guides/account-reads.md:99](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [apps/docs/content/guides/account-reads.md:175-182](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md)).
- **Account fetching/decoding — cache gap is architectural, not just documentation.** `useAddressRead()` keeps `data`, `loading`, and `error` in per-composable `shallowRef`s; sharing across mounts requires the separate keyed SWR adapters, whose cache is a module-level `Map` capped at 1024 entries with `clearSwrCache()` and `deleteSwrKey()` as the only invalidation API ([packages/vue/src/composables/use-address-read.ts:44-46](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts), [packages/vue/src/swr.ts:40-79](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts)). The address composables themselves do not consult that cache, so two mounted `useBalance()` components for the same address each read independently ([packages/vue/src/composables/use-address-read.ts:87-102](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts), [packages/vue/src/composables/useBalance.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useBalance.ts)).
- **Transaction reliability — partial implementation.** `useSignAndSendTransaction()` returns after submission unless `confirm: true` is passed, tracks `sending`/`confirming` separately, and preserves the signature when confirmation fails or times out ([packages/vue/src/composables/useSignAndSendTransaction.ts:29-42](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransaction.ts), [packages/vue/src/composables/useSignAndSendTransaction.ts:66-103](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransaction.ts), [apps/docs/content/guides/transactions.md:208](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). `confirmTransactionSignature()` polls `getSignatureStatuses` on a client-side deadline, treats a never-seen signature as `TRANSACTION_NOT_FOUND`, and a seen-but-unconfirmed signature as `TRANSACTION_TIMEOUT`; Kit's subscription-based confirmation path is explicitly not used because the wallet has already submitted the transaction ([packages/core/src/transaction.ts:146-192](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [packages/core/src/transaction.ts:194-249](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts)). The public send options are limited to `skipPreflight`, `maxRetries`, `minContextSlot`, and `preflightCommitment`; there is no library-level resubmit manager, durable-nonce helper, blockhash-expiry guard, priority-fee policy, or post-timeout reconciliation composable in the exports/barrels ([apps/docs/content/guides/transactions.md:221-235](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [packages/core/package.json:27-108](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json), [packages/vue/src/index.ts:1-46](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)). The docs put the burden on the app: keep the signature visible, check status after timeout, and avoid duplicate retries ([apps/docs/content/guides/transactions.md:324-333](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)).
- **Transaction reliability — raw-byte boundary and client/payer split.** Wallet signing APIs accept only serialized `Uint8Array` wire transactions; base64 strings, transaction objects, and instruction lists are not accepted, so app code must compile and encode with Kit helpers ([apps/docs/content/guides/transactions.md:210-219](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). The example transfer panel hand-builds the system instruction, fetches a blockhash, compiles the message, and encodes it before calling `useSignAndSendTransaction()` ([examples/vue-vite/src/components/panels/TransferPanel.vue:100-137](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransferPanel.vue)). Client-sent transactions use a different path that requires a `payer`, and Nuxt cannot carry a payer in module config ([apps/docs/content/guides/transactions.md:78-86](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [packages/nuxt/src/module.ts:12-19](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts)).
- **Token operations — reads only.** Core exports a `token-accounts` subpath documented as "stateless SPL Token account reads" with `getTokenAccountsByOwner`, `getTokenAccount`, and `getTokenBalance`, and those helpers only call `getTokenAccountsByOwner`/`getAccountInfo` and map `jsonParsed` results ([apps/docs/content/packages/core.md:234](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/core.md), [packages/core/src/token-accounts.ts:27-102](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/token-accounts.ts)). Vue only exposes `useTokenAccounts()` and `useTokenBalance()`; the latter returns raw `balance: bigint | null` and `decimals: number | null`, with no formatted amount, ATA address derivation, ATA creation, transfer, approve/revoke, mint, burn, or token-metadata helper in the public barrels ([packages/vue/src/index.ts:28-29](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts), [packages/vue/src/composables/useTokenBalance.ts:24-40](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useTokenBalance.ts), [packages/core/package.json:27-108](https://github.com/vue-solana/vue-solana/blob/main/packages/core/package.json)). The example dashboards mount no token panel; their Solana Pay panels only accept/display an optional SPL mint and never send a token transfer ([examples/vue-vite/src/App.vue:3-17](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/App.vue), [examples/vue-vite/src/components/panels/SolanaPayPanel.vue:135-147](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/SolanaPayPanel.vue), [apps/docs/content/guides/solana-pay.md:138-140](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md)).
- **Wallet UX — state layer exists, UI layer does not.** Public docs explicitly list "A built-in wallet modal or UI package", "Desktop native protocol-link adapters", "Server-side wallet prompts", and "Private-key or seed-phrase handling" as not included ([apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Capability gating is currently app code that reads `connected`, `canSignMessage`, and `canSignTransaction` to disable buttons ([apps/docs/content/guides/wallets.md:108-124](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Mobile flows add manual requirements: preserve UI state across wallet handoff/redirect, handle a one-time Local Network Access prompt, expect repeated MWA app-approval screens for Phantom, and call `handleSolanaIosWalletCallback()` early when using core iOS helpers directly ([apps/docs/content/guides/wallets.md:196-219](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:259](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). The exported provider for selected accounts is not a picker or modal ([packages/vue/src/components/SelectedWalletAccountProvider.ts:17-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts)).
- **SSR — safe but not ergonomic for data.** Nuxt's server context intentionally has no wallet discovery, persisted selection, RPC check, or bootstrap timer; `checkConnection`, `setWallet`, `refreshWallets`, and `selectWallet` are no-ops, and wallet state is inert until hydration ([packages/nuxt/src/runtime/server-plugin.ts:14-43](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts), [apps/docs/content/packages/nuxt.md:176](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)). SSR tests prove that data composables send no requests, open no streams, and start no timers during server rendering ([packages/vue/src/composables/ssr-inert.test.ts:14-58](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/ssr-inert.test.ts)). For data that must be in the initial HTML, the documented pattern is to create a private-config Nitro route, call `useServerSolanaClient()`, convert `bigint`s to strings, and fetch through `useAsyncData()` ([apps/docs/content/packages/nuxt.md:180-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)). The SWR module-level cache is explicitly per-process and is cleared at the start of each render; there is no general per-request cache scope outside that plugin hook ([packages/vue/src/swr.ts:31-34](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts), [packages/nuxt/src/runtime/server-plugin.ts:46-53](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts)).
- **Live data — powerful but raw.** The example live-data panel hand-wires `useRequest()` to two RPC calls, `useSubscription()` to `rpcSubscriptions.slotNotifications()`, and `useTrackedData()` to `getAccountInfo` + `accountNotifications` with two mapper functions ([examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue)). This is the intended low-level API, but there are no shipped convenience wrappers such as `useBalanceLive`, `useAccountInfoLive`, `useTokenAccountsLive`, or `useSignatureStatusLive` in the Vue barrel or Nuxt auto-import list ([packages/vue/src/index.ts:1-46](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts), [packages/nuxt/src/imports.ts:3-44](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts)). `useSignatureStatus()` specifically uses polling only despite docs that say "reads, polls, or subscribes" ([apps/docs/content/packages/vue.md:188](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/src/composables/useSignatureStatus.ts:158-205](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignatureStatus.ts)).
- **Program interaction — Kit is the builder, Vue layer stops at account scans and signers.** The transaction guide explicitly says to build messages with Kit helpers re-exported from `/kit` and the program client's instruction helpers ([apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). The example memo panel notes that the Kit mirror exports no instruction encoder and hand-asserts the memo instruction shape ([examples/vue-vite/src/components/LiveDataPanels.vue:110-123](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue)). There is no Vue composable that binds an IDL/generated program client to reactive account state, and `useProgramAccounts()` returns raw bytes rather than decoded typed accounts ([packages/vue/src/composables/useProgramAccounts.ts:35-84](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts), [packages/vue/src/index.ts:1-46](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)).
- **Error handling — normalized but coarse.** The public code list is a small fixed vocabulary; `normalizeSolanaError()` preserves an existing `SolanaError` and otherwise maps everything unknown to the caller's fallback such as `RPC_FAILURE`, while `isUserRejectedError()` only recognizes code `4001` or messages containing "user rejected"/"user denied" ([packages/core/src/errors.ts:3-31](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [packages/core/src/errors.ts:100-132](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts)). The docs tell apps to map stable codes to their own UI strings, not to show raw `cause`, and to decide retryability manually for `RPC_FAILURE`/`TRANSACTION_TIMEOUT` ([apps/docs/content/guides/errors.md:27-44](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/errors.md), [apps/docs/content/guides/errors.md:134-161](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/errors.md)). No exported helper decodes program-specific/custom errors or Kit numeric error codes, and the root barrels expose only the error classes/codes/normalizer already described ([packages/core/src/index.ts:1-15](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts), [packages/vue/src/index.ts:1-46](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)).

### Inferences

- **Architectural/library-level gaps** are: no first-class reliable transaction lifecycle beyond submit + optional poll-confirm; no built-in wallet picker/capability-aware UI; no live convenience wrappers over the generic reactive-store bridges; no shared account/token cache or invalidation model in the address-read composables; no typed program-account decoding/pagination; no token write-operation toolkit; no integrated Nuxt SSR data bridge; and no actionable program-error decoder ([packages/vue/src/composables/useSignAndSendTransaction.ts:46-103](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransaction.ts), [apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue), [packages/vue/src/composables/useProgramAccounts.ts:56-84](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts), [apps/docs/content/packages/nuxt.md:180-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)).
- **Missing examples/docs only** are the stale `watch: true`/"subscribe" descriptions and the lack of a runnable token-operations panel or wallet-modal demo; the underlying APIs for those examples either do not exist or are state-only, so examples alone would not close the functional gap ([apps/docs/content/packages/vue.md:433-464](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/src/components/SelectedWalletAccountProvider.ts:17-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts), [examples/vue-vite/src/App.vue:3-17](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/App.vue)).
- The current design makes the library a set of composable building blocks; adding higher-level features should preserve the existing subpath/bundle discipline so optional UI or heavyweight deps do not land in every root import ([packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts), [packages/vue/package.json:27-204](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json)).

### Gaps

- No usage or support data was available to size demand for token writes, program-account pagination, or desktop native wallets.
- The audit did not inspect GitHub issues, so it cannot distinguish "missing" from "requested and rejected" for any candidate.
- No compatibility matrix for third-party program-client/decoder libraries was reviewed; a decoder abstraction's integration surface is therefore only roughly scoped.
- No performance measurement was made of the current confirmation polling versus a websocket-based approach, so the ranking treats reliability/UX rather than throughput as the benefit.

## Which missing capabilities should stay in raw `@solana/kit`, an external package, or the app?

### Takeaway

Vue Solana should keep owning Vue lifecycle/reactivity, wallet state/UX, Nuxt integration, and error/state semantics, but should not reimplement Kit's transaction/message codecs, program-specific codegen/IDL clients, server-side authentication, general-purpose query caching, archival indexing, or secret custody ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/guides/message-signing.md:104-108](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/message-signing.md)). The safest split is "Kit for primitives, Vue Solana for reactive workflows, external services for indexing/auth/custody".

### Cited Findings

- **Raw Kit remains the source of truth for messages/instructions.** Every package's `/kit` entry is a full `@solana/kit` mirror, and the docs tell developers to build transaction messages with Kit helpers and a program client's instruction helpers rather than asking Vue Solana to curate those APIs ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/packages/vue.md:169](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md)).
- **Server-side SIWS verification and nonce/session management are app responsibilities.** Client-side signature checks are explicitly best-effort and skipped where WebCrypto/Ed25519 is unavailable; the docs require server verification of domain, URI, nonce, expiry, and session creation ([apps/docs/content/guides/message-signing.md:43-64](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/message-signing.md), [apps/docs/content/guides/message-signing.md:104-108](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/message-signing.md)).
- **Broad account indexing is outside the library.** The account-read guide warns that program account scans can be expensive and explicitly recommends narrow filters, `dataSlice`, caching, pagination, indexing, or dedicated RPC infrastructure for production ([apps/docs/content/guides/account-reads.md:99](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [apps/docs/content/guides/account-reads.md:175-182](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md)).
- **General cache/query semantics are deliberately not part of the SWR layer.** The module documentation says there is intentionally no `useAction` adapter because actions are imperative mutations, not cacheable reads, and the cache is a dependency-free module-level `Map` requiring server-side namespace/clear discipline ([packages/vue/src/swr.ts:18-38](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts)).
- **Secret custody is intentionally excluded from Nuxt.** `payer`/`payerSecretKey` are omitted from module options, server utilities strip them at runtime, and the docs tell users to keep RPC URLs/API keys in private runtime config and funded keys on a trusted server/relayer ([packages/nuxt/src/module.ts:12-19](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts), [packages/nuxt/src/runtime/server.ts:5-27](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server.ts), [apps/docs/content/guides/rpc-and-clusters.md:121-137](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/rpc-and-clusters.md)).
- **Wallet sources that need separate protocols should stay separate until justified.** Wallet support is built on Wallet Standard, the Android MWA package, and iOS-specific links; desktop native protocol-link adapters are explicitly "not supported yet" with only reserved metadata, and the docs say manual wallet objects should keep key custody inside the provider ([apps/docs/content/guides/wallets.md:12-17](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:29-37](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:221-268](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)).
- **Solana Pay's security boundary stays in the app/server.** Transaction request URLs are parsed/encoded only; the linked endpoint and authorization are the app's responsibility, scanned data must be confirmed by a user, there is no auto-send path, and `reference` alone is not proof of payment ([apps/docs/content/guides/solana-pay.md:43-57](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md), [apps/docs/content/guides/solana-pay.md:138-140](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md), [apps/docs/content/guides/solana-pay.md:193-200](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md)).
- **Heavy optional dependencies must remain behind subpaths.** The root barrels deliberately exclude Buffer, iOS, and mobile-wallet paths for bundle-size reasons, and the docs instruct named-import-and-call usage for the Buffer helper because packages are marked `sideEffects: false` ([packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts), [apps/docs/content/packages/vue.md:169](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/package.json:23-25](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/package.json)).

### Inferences

- Program-specific instruction builders, account layouts, and IDL decoding should normally come from a generated program client; Vue Solana can provide a generic decoded-account store, lifecycle helpers, and error mapping, but should not become an IDL/codegen framework.
- Auth backends, indexed/archival queries, and funded-key custody belong outside the browser library because the current docs already establish those trust boundaries ([apps/docs/content/guides/message-signing.md:104-108](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/message-signing.md), [apps/docs/content/guides/account-reads.md:175-182](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [apps/docs/content/guides/rpc-and-clusters.md:121-137](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/rpc-and-clusters.md)).
- A wallet modal/UX layer is a good library candidate only if shipped as an opt-in subpath/package, because the current state layer is intentionally headless and root bundles are size-sensitive ([packages/vue/src/components/SelectedWalletAccountProvider.ts:17-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts), [packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts)).

### Gaps

- No benchmark or dependency-cost analysis was performed for candidate wrappers, so the "keep out of root" conclusion is based on documented bundle policy rather than new measurements.
- No ecosystem compatibility survey was performed for every program-client framework, so the boundary around a generic decoder registry is provisional.
- No legal/security review was performed for token/NFT metadata providers that a future token toolkit might need.

## Which eight next features rank highest by developer value, uniqueness versus raw Kit, and implementation effort?

### Takeaway

Ranking the evidence-derived opportunities gives a top tier of reliable transaction lifecycle, wallet UX, and live account/token data: each addresses a documented absence or a raw wiring burden in a way raw Kit does not solve ([apps/docs/content/guides/transactions.md:208-333](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue)). The next tier adds typed program/token/SSR/errors/simulation helpers whose value is high but whose scope overlaps more with external program clients or narrower user segments ([apps/docs/content/guides/account-reads.md:99](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [apps/docs/content/packages/core.md:234](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/core.md), [apps/docs/content/packages/nuxt.md:180-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)). Effort below is relative API-surface sizing (S/M/L), not a schedule commitment.

### Cited Findings

1. **Reliable transaction lifecycle composable (`useTransactionLifecycle` / `useSendAndConfirm`).** Problem: apps receive a signature after RPC submission but must opt into confirmation, keep the signature across timeout, check status before retrying, and build their own progress UI; the core confirmer polls `getSignatureStatuses` and distinguishes not-found from timeout, while a timeout still requires app reconciliation ([packages/vue/src/composables/useSignAndSendTransaction.ts:46-103](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransaction.ts), [packages/core/src/transaction.ts:146-249](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [apps/docs/content/guides/transactions.md:208](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/guides/transactions.md:324-333](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). Target user: any dapp with payments, trades, minting, or high-value writes. Rough scope (M-L): a composable that accepts raw bytes or a plan, exposes a status timeline (`building`, `signing`, `submitted`, `processed`, `confirmed`, `finalized`, `failed`, `unknown`), preserves signatures, supports abort/websocket confirmation where available, offers safe retry hooks keyed by signature, and surfaces explorer links using the cluster rule already documented ([apps/docs/content/guides/transactions.md:239-250](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). Uniqueness versus raw Kit is high because Kit supplies send/confirm primitives but not Vue state, retry safety, or UI semantics ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts), [apps/docs/content/guides/transactions.md:78-86](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)).
2. **Headless wallet picker plus optional accessible Vue components.** Problem: `useWallets()`/`useWallet()` and selected-account state are headless, while docs explicitly exclude a wallet modal and require manual capability checks and mobile-handoff UI preservation ([packages/vue/src/composables/useWallets.ts:3-12](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useWallets.ts), [apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:108-124](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [apps/docs/content/guides/wallets.md:196-219](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Target user: every app onboarding a wallet user; especially teams that cannot afford Wallet Standard/mobile edge-case UI. Rough scope (M-L): `WalletList`/`ConnectButton`/`AccountPicker` components or an unstyled headless composable that filters discovered wallets, gates actions by `canSign*`, uses the existing selected-account persistence/filtering context, renders normalized wallet errors, and defers all work to the client ([packages/vue/src/composables/useSelectedWalletAccount.ts:20-52](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSelectedWalletAccount.ts), [packages/vue/src/components/SelectedWalletAccountProvider.ts:17-35](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts)). Uniqueness is high: no amount of raw Kit gives discovery, platform labels, wallet exclusivity, or iOS/MWA handoff guidance ([apps/docs/content/guides/wallets.md:8-17](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [packages/vue/src/plugin/wallet-registry.ts:170-203](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts)).
3. **Live account/balance/token convenience layer with coherent invalidation.** Problem: the shipped live layer requires app code to choose a request source, subscription source, and two mappers, while ordinary address reads only refresh on mount/watch and the SWR cache must be keyed and cleared manually ([examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue), [packages/vue/src/composables/use-address-read.ts:87-102](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-address-read.ts), [packages/vue/src/swr.ts:31-34](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/swr.ts)). Target user: dashboards, explorers, wallets, and trading UIs. Rough scope (M): `useBalanceLive`, `useAccountInfoLive`, `useTokenAccountsLive`, `useTokenBalanceLive`, and a signature-status live variant built on `useTrackedData`, with cluster/address cache keys and explicit invalidation after writes; this also resolves the stale docs promise that account info/signature status can "watch"/"subscribe" ([apps/docs/content/packages/vue.md:433-464](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [apps/docs/content/packages/vue.md:188](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/vue.md), [packages/vue/src/composables/useTrackedData.ts:122-140](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useTrackedData.ts)). Uniqueness is high because the reactive-store bridge is Vue-specific even though the RPC calls are Kit-generic ([packages/vue/src/composables/useSubscription.ts:65-81](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSubscription.ts)).
4. **Typed program-account decoding and pagination.** Problem: `useProgramAccounts()` returns raw bytes and a single `getProgramAccounts` response, while the docs warn about expensive scans and recommend pagination/indexing; apps must hand-write decoders and cursors ([packages/vue/src/composables/useProgramAccounts.ts:35-84](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useProgramAccounts.ts), [apps/docs/content/guides/account-reads.md:99](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md), [apps/docs/content/guides/account-reads.md:175-182](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/account-reads.md)). Target user: apps built on custom programs that do not want a full generated client for simple reads. Rough scope (M): `defineAccountCodec()`, `useDecodedAccount(s)` accepting a codec plus the existing address/filter options, typed filter helpers, and optional page/cursor state; deliberately leave IDL/codegen and indexing to program-client/indexer packages ([apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [examples/vue-vite/src/components/LiveDataPanels.vue:110-123](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue)). Uniqueness is medium-high: Kit provides bytes and filters, not Vue decoding/pagination state.
5. **Opt-in token operations toolkit.** Problem: token support is read-only and exposes raw `bigint`/`decimals`; there is no ATA derivation/creation, transfer, approve/revoke, mint, burn, or amount formatting helper in the public surface ([apps/docs/content/packages/core.md:234](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/core.md), [packages/core/src/token-accounts.ts:27-102](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/token-accounts.ts), [packages/vue/src/composables/useTokenBalance.ts:24-40](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useTokenBalance.ts)). Target user: token dashboards, merchant tools, simple SPL payment flows. Rough scope (L): thin composables/helpers for associated-token-account addresses, existence checks/creation instructions, transfer/approve/mint/burn builders that feed the existing wallet/client send paths, and human-readable amount formatting; it should compose with generated token program clients rather than replace them ([apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/guides/transactions.md:210-219](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). Uniqueness is medium because token instruction builders exist elsewhere, but the reactive wallet-plus-read integration would be genuinely useful ([apps/docs/content/guides/solana-pay.md:138-140](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/solana-pay.md)).
6. **Nuxt SSR data bridge (`useSolanaAsyncData` / server read helpers).** Problem: SSR is safe but the documented workflow requires a Nitro route, private runtime config, `useServerSolanaClient()`, `bigint` serialization, and `useAsyncData()` wiring repeated per page ([apps/docs/content/packages/nuxt.md:176-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md), [packages/nuxt/src/runtime/server-plugin.ts:14-43](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts)). Target user: Nuxt teams that need SEO/fast first paint and private RPC credentials. Rough scope (M): a Nuxt-specific composable that takes a client RPC request factory and serialization policy, runs server-side via the existing server utility, hydrates into the payload, and shares a request-scoped cache with the client composables; preserve the current secret-stripping behavior and inert server context ([packages/nuxt/src/runtime/server.ts:5-27](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server.ts), [packages/nuxt/src/runtime/server-plugin.ts:46-66](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server-plugin.ts)). Uniqueness is very high because this is Nuxt-specific; value ranks below the top three because the manual pattern already works ([apps/docs/content/guides/rpc-and-clusters.md:135-185](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/rpc-and-clusters.md)).
7. **Actionable error decoding and recovery model.** Problem: errors are stable but coarse, unknown failures collapse to `RPC_FAILURE`, and users are told to map codes and decide retries themselves; no public helper decodes program-specific/custom errors ([packages/core/src/errors.ts:3-31](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [packages/core/src/errors.ts:100-132](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [apps/docs/content/guides/errors.md:27-44](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/errors.md), [apps/docs/content/guides/errors.md:134-161](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/errors.md)). Target user: all app developers, especially those localizing UI and handling support tickets. Rough scope (S-M): preserve original numeric/cause data, add optional program-error registries, expose `retryable`, `userMessageKey`, and recovery action metadata while keeping `code`/`cause` compatibility; do not replace server-side auth verification ([apps/docs/content/guides/message-signing.md:104-108](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/message-signing.md)). Uniqueness is medium: Kit has error codes, but Vue Solana can own UI-facing normalization across wallet/RPC/signer paths ([packages/vue/src/index.ts:48-56](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)).
8. **Simulation preview and fee/blockhash policy helpers.** Problem: simulation already returns normalized logs, balance changes, loaded addresses, return data, and units consumed, and the docs stress that simulation is not a guarantee; the app still has to present that data and decide freshness/priority fees ([packages/core/src/transaction.ts:88-144](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [apps/docs/content/guides/transactions.md:28-59](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). Target user: advanced users and apps on congested clusters. Rough scope (S-M): `useSimulationPreview()` with diffable balance/token changes, compute-unit summary, blockhash-age warning, and optional priority-fee suggestion fed into the existing send options; require no payer for simulation, matching the current composable behavior ([apps/docs/content/guides/transactions.md:59](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [apps/docs/content/guides/transactions.md:221-235](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). Uniqueness is medium because compute-budget/fee estimation belongs partly to Kit/RPC, while the reactive interpretation layer is Vue Solana's ([packages/core/src/kit.ts:199-213](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/kit.ts)).

### Inferences

- Features 1-3 should be evaluated first because each addresses an explicit absence or hand-wiring example: no reliable lifecycle wrapper, no wallet UI package, and no account-level live convenience layer despite raw primitives and stale docs ([apps/docs/content/guides/wallets.md:48-53](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [examples/vue-vite/src/components/LiveDataPanels.vue:46-103](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/LiveDataPanels.vue), [apps/docs/content/guides/transactions.md:324-333](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)).
- Feature 4 should stay generic and codec-driven; feature 5 should be opt-in because token instruction builders are available from program clients and the current package deliberately keeps heavy optional paths out of root barrels ([apps/docs/content/guides/transactions.md:8-10](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [packages/core/src/index.ts:17-34](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/index.ts)).
- Feature 6 is the clearest Nuxt differentiator, but rank 6 reflects that a working manual pattern is already documented ([apps/docs/content/packages/nuxt.md:180-230](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/packages/nuxt.md)).
- Features 7 and 8 are lower-effort force multipliers that can be added to existing composables without new package boundaries, but they do not close as large a UX gap as the top three ([packages/core/src/errors.ts:100-132](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [packages/core/src/transaction.ts:95-144](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts)).

### Gaps

- Effort ratings are relative estimates based on API scope; no team-capacity or scheduling information was used.
- No user interviews, issues, or telemetry were reviewed, so the ranking cannot claim measured demand.
- No prototype or compatibility spike was performed for websocket signature subscriptions, program codecs, token program-client APIs, or Nuxt payload hydration.
- No bundle-size budget was measured for adding optional UI components, so the exact packaging of feature 2 remains open.
