## 3. Which missing capabilities repeatedly appear in Solana developer discussions, especially around transaction errors, account/token reads, wallet UX, SSR, mobile wallets, program calls, and testing?

### Takeaway

### Inferences

- "Transaction errors" usually means one of three different needs: preflight simulation, decoding custom program errors, and distinguishing sent/confirmed/failed states. A single feature that exposes normalized simulation plus error context addresses a broadly reusable need.
- Token-account problems are not just balance reads; developers need owner-level aggregation and deterministic handling of multiple ATAs.
- Mobile-wallet pain is not a single missing feature; it is session lifecycle, authorization, app identity, account state, and send path reliability.
- SSR is a strong fit for Nuxt, but the observed demand comes from the project's recent implementation choices and general Nuxt patterns rather than users explicitly asking for Solana SSR.

### Gaps

- Discord/public chat transcripts were not accessible in this research pass.
- Some Stack Exchange views/answers may include spam or unrelated traffic; view counts are used only as a rough attention signal.
- No quantitative count of "Vue users" among Stack Exchange questions was possible because the API searches text, not user frameworks.

## 6. Demand-ranked shortlist of next features and strongest evidence

### Takeaway

Ranking weights direct Vue/Nuxt requests highest, then recurrence across adjacent Solana tooling, then npm/release signals. Features already shipped on 2026-11-18/19 are included only as "extend/harden", not as greenfield recommendations.

1. **Unified wallet-session/account-state reliability layer** — strongest direct Vue-specific demand and the most repeated recent vue-solana fixes. Evidence: Vue MWA request #50 ("can not use Vue on Android/iOS"), reconnect/publicKey issues #49/#59/#70, iOS two-tab issue #72, and vue-solana PRs #122/#125/#128/#137 documenting Phantom/MWA hangs and missing prompts. A reusable feature would centralize stable app identity, reconnect/reauthorize, account-change synchronization, and actionable failure states across Wallet Standard/MWA/iOS. — [Vue #50](https://github.com/lorisleiva/solana-wallets-vue/issues/50) · [Vue #70](https://github.com/lorisleiva/solana-wallets-vue/issues/70) · [Vue #72](https://github.com/lorisleiva/solana-wallets-vue/issues/72) · [vue-solana #137](https://github.com/vue-solana/vue-solana/pull/137)
2. **Extend transaction simulation into user-facing error diagnosis/decoding** — high recurrence, and a natural follow-on to the just-shipped `useSimulateTransaction()`. Evidence: SE #22685 (1,895 views), #23532 (957 views), #24426, upstream #2755/#3214/#3758/#3930, and vue-solana #144/#152. A reusable Vue feature could turn simulation logs/balance changes/custom codes into a normalized display model and actionable messages. — [SE #22685](https://solana.stackexchange.com/questions/22685/phantom-transaction-reverted-during-simulation-but-it-works-if-confirmed) · [web3.js #2755](https://github.com/solana-foundation/solana-web3.js/issues/2755) · [vue-solana #152](https://github.com/vue-solana/vue-solana/pull/152)

Evidence: vue-solana PR #151's `statusCode=429` and "suite-wide" conclusion, PR #149's `rpc_failure` ambiguity, SE #24593's HTTP 429, #24541's faucet rate limit, and #23723's devnet rate-limit demo problem. — [vue-solana #151](https://github.com/vue-solana/vue-solana/pull/151) · [SE #24593](https://solana.stackexchange.com/questions/24593/how-can-i-efficiently-track-spl-token-holder-counts-and-changes-without-hitting) · [SE #23723](https://github.com/solana.stackexchange.com/questions/23723/how-to-give-demo-for-an-solana-dapp-that-is-running-on-a-local-validator)
4. **Owner-aware token account discovery/balance helpers** — recurring across simple and advanced questions. Evidence: SE #24499 (multiple token accounts), #24509 ("which token account"), #24593 (avoid double-counting owners), Vue-specific #13000, and upstream program-filter issue #3975. — [SE #24499](https://solana.stackexchange.com/questions/24499/what-if-a-user-has-2-token-accounts-for-same-token) · [SE #13000](https://github.com/solana.stackexchange.com/questions/13000/getorcreateassociatedtokenaccount-method-always-returns-tokenaccountnotfounderro) · [web3.js #3975](https://github.com/solana-foundation/solana-web3.js/issues/3975)

Evidence: SE #23723 says extension wallets lack localnet support while devnet is rate-limited; #23476 asks about pre-initialized SPL accounts in tests; #24541 asks for devnet SOL; vue-solana PR #151 documents CI instability. — [SE #23723](https://solana.stackexchange.com/questions/23723/how-to-give-demo-for-an-solana-dapp-that-is-running-on-a-local-validator) · [SE #23476](https://solana.stackexchange.com/questions/23476/how-to-create-already-existing-initialized-spl-token-accounts-in-anchor-rust-te) · [vue-solana #151](https://github.com/vue-solana/vue-solana/pull/151)

Evidence: PR #154 adds request-scoped server RPC and `useAsyncData()`/Nitro pattern; Nuxt modules issue #1506 asks for listing; general Nuxt 2026 tutorials emphasize SSR, `useAsyncData`, and Nitro. — [vue-solana #154](https://github.com/vue-solana/vue-solana/pull/154) · [nuxt/modules#1506](https://github.com/nuxt/modules/issues/1506) · [DuckDuckGo results](https://html.duckduckgo.com/html/?q=Vue+Nuxt+Solana+tutorial+2026)

### Inferences

- If forced to choose one, the evidence points to **wallet-session/account-state reliability** as the next feature: it has the longest and most explicit Vue-user request trail, and the project itself shipped five MWA/wallet fixes in November 2026.
- If the goal is breadth rather than Vue-specificity, **simulation-aware error diagnosis** and **RPC resilience** are the strongest adjacent-tooling demands.
- Avoid choosing protocol-specific redemption flows, showcase/version upkeep, or another QR scanner fix as the next strategic feature; those are narrow or already addressed.
