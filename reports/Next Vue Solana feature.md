# Ship a Transaction Activity Feed

The next feature should be a **read-only transaction history/activity API**: `getTransactionHistory()` in core, `useTransactionHistory()` in Vue, and `useSolanaTransactionHistory()` in Nuxt. It wins because it closes the lifecycle loop that the project has nearly completed: simulation shipped in PR #152 on 2026-11-18, Nuxt SSR server RPC in PR #154 on 2026-11-19, yet the library still offers no way to list what happened to an address after signing and sending ([PR #152](https://github.com/vue-solana/vue-solana/pull/152), [PR #154](https://github.com/vue-solana/vue-solana/pull/154)). The need is visible in the shipped docs: users are told to preserve signatures, check status before retrying, and hand-build cluster-aware explorer URLs, while the only current use of `getSignaturesForAddress` is Solana Pay settlement lookup and the Playwright mock returns an empty array ([transactions guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [solana-pay-confirmation.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/solana-pay-confirmation.ts), [e2e/helpers.ts](https://github.com/vue-solana/vue-solana/blob/main/e2e/helpers.ts)). Wallet reliability has stronger explicit Vue-flavored demand, but the last release line already absorbed much of it through MWA session fixes, signer adapters, exclusive connect, selected-account persistence, and iOS flows; another wallet feature would mostly be hardening ([PR #146](https://github.com/vue-solana/vue-solana/pull/146), [wallet-registry.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/plugin/wallet-registry.ts)). Token actions, Anchor integration, wallet modals, and RPC failover are larger product bets with money movement, catalogs, UI ownership, or client-architecture churn. Transaction history is the only candidate that is missing, broadly useful, Kit-native, SSR-safe, dependency-free, and testable with an RPC mock that already exists; its first slice should return raw signature metadata and pagination, not decoded program semantics.

## The unmet gap sits after submission, not before it

The repository has reached the point where “another Kit wrapper” is rarely the right answer. As of 2026-11-21 the published packages were at 4.4.0, with five releases in four days—4.2.0 signer adapters, 4.2.1 validation, 4.2.2 Solana Pay/RPC hardening, 4.3.0 simulation, and 4.4.0 SSR—and last-30-day downloads of roughly 4,825 core, 4,760 Vue, and 4,510 Nuxt, against 1,951/1,867/1,689 in the prior 30 days ([releases API](https://api.github.com/repos/vue-solana/vue-solana/releases?per_page=30), [core downloads](https://api.npmjs.org/downloads/range/2025-11-21:2026-11-21/@vue-solana%2fcore), [community-demand.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/community-demand.md)). That is an early-stage but accelerating adoption curve with no user issues and Discussions disabled, so feature priority comes from maintainer-observed workflow gaps rather than votes; the GitHub API showed 155 issue-list entries, all pull requests, and the `is:issue` page returned zero results ([repository API](https://api.github.com/repos/vue-solana/vue-solana), [issues page](https://github.com/vue-solana/vue-solana/issues?q=is%3Aissue)). In that situation, the right next feature is one that makes the existing stack feel complete rather than one that opens a new maintenance frontier.

The strongest remaining workflow gap is “what happened to my transaction?” `packages/core/src/transaction.ts` already has `signAndSendTransaction()`, `simulateTransaction()`, and `confirmTransactionSignature()`; `packages/vue/src/composables/useSignAndSendTransaction.ts` tracks `sending`/`confirming` and preserves a signature across confirmation failure; `useSignatureStatus()` and `useTransactionConfirmation()` handle post-send status; but no core or Vue export lists signatures for an address ([transaction.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/transaction.ts), [useSignAndSendTransaction.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/useSignAndSendTransaction.ts), [Vue index.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/index.ts)). The docs explicitly warn that a timeout requires checking signature status before retrying and show how to construct explorer links, but offer no library-level activity feed to find or display those signatures ([transactions guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md)). The strategy notes reached the same conclusion from a different direction: they scored transaction history first at 87, ahead of priority-fee helpers at 82 and error decoding at 76, precisely because it is read-only, uses the existing `getSignaturesForAddress` mock seam, and fits the existing transactions guide ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).

Wallet demand is real but mostly already answered. The community notes cite `solana-wallets-vue#50` from 2023-04-02 saying developers “can not use Vue on Android/iOS” without MWA, plus reconnect/publicKey issues #49, #59, #70, and iOS two-tab issue #72, while vue-solana PRs #122, #125, #128, and #137 document MWA hangs, rejected cached tokens, wrong session routing, and missing payment approvals ([Vue #50](https://github.com/lorisleiva/solana-wallets-vue/issues/50), [Vue #70](https://github.com/lorisleiva/solana-wallets-vue/issues/70), [vue-solana #137](https://github.com/vue-solana/vue-solana/pull/137)). Those are the strongest direct Vue complaints in the notes, but the current repository already has lazy Android MWA registration, iOS deep links and callbacks, wallet-standard signature verification, selected-account persistence with cross-tab storage sync, and an exclusive-connect sweep over discovered wallets; the repo audit documents those implementations in `packages/core/src/mobile-wallet.ts`, `packages/core/src/ios-wallet/`, `packages/vue/src/composables/useSelectedWalletAccount.ts`, and `packages/vue/src/plugin/wallet-registry.ts` ([repo-gap-audit.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md)). That makes wallet work a bug-and-polish track, not the cleanest next headline feature.

## History wins on five decision axes, while alternatives carry larger bills

On **user value**, a history feed serves every app with a wallet address: dashboards can show recent activity, payment UIs can reconcile a timeout, and support teams can start from a signature list instead of raw explorer links. On **product differentiation**, Kit supplies the typed RPC call but not Vue state, supersede/abort behavior, pagination, reactive address sources, or a consistent error model—the same “reactive workflow over Kit” layer that already distinguishes this library ([Kit README](https://github.com/anza-xyz/kit/blob/main/README.md), [repo-gap-audit.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md)). On **ecosystem timing**, Kit 8.6.0 was stable on 2026-10-28, so the underlying `getSignaturesForAddress` surface is mature, while many official plugins remain 0.x and their APIs churned through 7.x/8.x; a feature that uses core Kit types avoids that volatility ([Kit releases](https://github.com/anza-xyz/kit/releases), [kit-ecosystem.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/kit-ecosystem.md)). On **architecture fit**, the slice adds one core subpath, one Vue composable, one Nuxt alias, and no runtime config, secret handling, npm dependency, static heavy edge, or wallet-protocol change. On **implementation risk**, the failure modes are bounded: a bad page is a UI bug, whereas a bad token action can move funds or a bad wallet change can break signing.

## The smallest coherent slice is a paginated, read-only activity list

The first release should be deliberately boring. Its contract should be one core function that calls `rpc.getSignaturesForAddress(address, { before, until, limit, commitment })`, returns the RPC’s stable fields as normalized items—`signature`, `slot`, `blockTime` where available, `err`, and `confirmationStatus` where available—and adds only `hasMore`/cursor metadata derived from page length; transport failures should go through the existing `normalizeSolanaError(..., "RPC_FAILURE")` pattern, and malformed limits should be `INVALID_INPUT` rather than a transport error ([errors.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/errors.ts), [strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)). It should not fetch full parsed transactions in v1; developers who need instruction detail can still call Kit methods with a returned signature, and decoding stays out of the core bundle.

Explicit deferrals are part of the product definition. Do not decode instructions, categorize token transfers, parse memos beyond raw fields, or invent human-readable program labels; that turns a read helper into an indexer and program catalog. Do not add automatic resubmission, retry-on-timeout, transaction replacement, priority-fee automation, server-side persistence, or an indexing database; the docs currently require checking status before retrying, and Nuxt deliberately strips `payer`, `payerSecretKey`, and `wallet` from public config and server utilities ([transactions guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [module.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts), [server.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/runtime/server.ts)). Also defer a history component, wallet modal, Anchor/IDL helpers, Token-2022 actions, RPC failover, and versioned docs; each is a separate strategic bet with a larger maintenance profile than this slice ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).

## The disagreement is about remaining pain, not about product boundaries

The researchers differ sharply at the top of their lists, and the differences are informative. The community-demand notes rank unified wallet-session/account-state reliability first on the longest direct Vue issue trail; the kit-ecosystem notes rank an official-plugin-backed reactive wallet adapter first because Kit’s wallet plugin now covers discovery, reconnect, account switching, signer mapping, SIWS, and verification but ships React hooks only; the repo-gap audit ranks a reliable transaction lifecycle composable first; and the competitor analysis points to token mutations and simulation/debug as the highest-value new primitives ([community-demand.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/community-demand.md), [kit-ecosystem.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/kit-ecosystem.md), [repo-gap-audit.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/repo-gap-audit.md), [competitor-analysis.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/competitor-analysis.md)). The feasibility notes break the tie by scoring small-slice cost and burden, putting history first; that score is a judgment, not a measurement, but it is the judgment most consistent with the shipped source ([strategy-feasibility.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)).

Resolution follows three rules. First, distinguish **demand** from **remaining gap**: wallet/MWA pain is the best-evidenced demand, but the repository has already spent multiple releases on it, while history has no API at all. Second, prefer features that do not create catalogs or custody obligations: token actions, Anchor helpers, error registries, and wallet UI each require ongoing judgments about programs, wallets, fees, accessibility, or provider behavior, whereas raw signature metadata is stable. Third, prefer reversible slices with existing test seams: history can land behind a new subpath, be exercised through the current mock RPC, and later feed diagnostics without changing client construction. The official wallet plugin argument is a good future architecture discussion, but swapping a working custom wallet layer that already handles MWA/iOS specifics is not a net-new user feature and would pull in 0.x plugin and React/UI-registry surface risk ([kit-ecosystem.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/kit-ecosystem.md)).

The main uncertainty is demand measurement, not technical feasibility. There are no repository issues, no Discussions, no accessible Reddit/Discord corpus, no user interviews, and npm downloads cannot distinguish humans from CI or identify why users stayed; the November 8 download spike around the QR scanner sequence is correlation only ([community-demand.md](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/community-demand.md)). This recommendation is therefore a product bet under uncertainty: choose the feature that makes the existing Kit-first stack visibly complete and keeps future options open.

## Conclusion

The decision implies that Vue Solana’s next advantage is not broader API coverage but better ownership of the state between network events and the user. History is the smallest surface where that ownership is both obvious and reusable, and it creates a natural foundation for a later diagnostics view that joins signatures, simulation logs, and normalized errors without reopening wallet or client architecture.

Treat wallet reliability, fees, token actions, and live-data conveniences as the next queue, not this release. Shipping history first keeps the monorepo’s hard-won constraints intact—single Kit copy, lean eager bundles, SSR-safe Nuxt boundaries, headless composables—while giving every app a concrete answer to the question its transaction guide already asks users to handle manually: what happened after I sent it?
