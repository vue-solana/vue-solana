# Ship UI Recipes, Not a Library

Do not publish a UI library yet. The best next features for Vue Solana remain headless, and the UI work should ship first as copyable recipes plus a few small view-model helpers around composables that already exist. The repository has **zero issues, 163 pull requests, and Discussions disabled**, so there is no direct user request for a modal, button, toast, or any named component; the project’s own README and wallets guide explicitly say apps should build their own wallet-selection UI ([repo API](https://api.github.com/repos/vue-solana/vue-solana), [issue search](https://api.github.com/search/issues?q=repo%3Avue-solana%2Fvue-solana+is%3Aissue&per_page=1), [PR search](https://api.github.com/search/issues?q=repo%3Avue-solana%2Fvue-solana+is%3Apr&per_page=1), [Discussions API](https://api.github.com/repos/vue-solana/vue-solana/discussions?per_page=100), [README](https://github.com/vue-solana/vue-solana/blob/main/README.md), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). The only explicit Vue component requests live in adjacent, stale projects and center on wallet modal triggers, connect-button labels, account dropdowns, and form-safe buttons—not toasts, token inputs, activity feeds, or scanner components ([solana-wallets-vue #58](https://github.com/lorisleiva/solana-wallets-vue/issues/58), [#57](https://github.com/lorisleiva/solana-wallets-vue/issues/57), [#22](https://github.com/lorisleiva/solana-wallets-vue/issues/22), [wallet-adapter #67](https://github.com/anza-xyz/wallet-adapter/issues/67)). Official Kit and Wallet Adapter stacks are deliberately headless and ship React hooks or React/CSS components, not Vue bindings ([kit-plugin-wallet README](https://raw.githubusercontent.com/anza-xyz/kit-plugins/main/packages/kit-plugin-wallet/README.md), [PACKAGES.md](https://raw.githubusercontent.com/anza-xyz/wallet-adapter/master/PACKAGES.md)). A separate UI package would inherit CSS, tokens, focus management, i18n, SSR hydration, mobile handoff, visual tests, and a fourth release surface that this monorepo currently avoids ([AGENTS.md](https://github.com/vue-solana/vue-solana/blob/main/AGENTS.md)). Over the 30 complete days to 2026-11-24, `@vue-solana/vue` had **4,962** downloads while React’s wallet UI had **936,428**, but the latter peers on React and `@solana/web3.js` v1 and the old official Vue UI package had **9** downloads, so that gap measures ecosystem age, not Vue demand ([Vue downloads](https://api.npmjs.org/downloads/range/2026-10-26:2026-11-24/@vue-solana%2fvue), [React UI downloads](https://api.npmjs.org/downloads/range/2026-10-26:2026-11-24/@solana%2fwallet-adapter-react-ui), [React UI registry](https://registry.npmjs.org/@solana%2Fwallet-adapter-react-ui), [Vue UI downloads](https://api.npmjs.org/downloads/range/2026-10-26:2026-11-24/@solana%2fwallet-adapter-vue-ui)). Queue fee-policy, diagnostics, token/portfolio, program-client reactivity, and bundle work ahead of `@vue-solana/ui`; if a package later becomes unavoidable, make it opt-in, unstyled, slot-driven, and start with a read-only activity list rather than a wallet picker.

## No one asked for a component, only for flows that work

The honest demand picture is thin and must be labeled as such. As of 2026-11-25 the Vue Solana repository reports **0 issues**, **163 PR entries**, and no open items, while the Discussions endpoint returns HTTP 410; PR authorship is overwhelmingly the maintainer and bots, so it records output rather than votes ([repo API](https://api.github.com/repos/vue-solana/vue-solana), [issue search](https://api.github.com/search/issues?q=repo%3Avue-solana%2Fvue-solana+is%3Aissue&per_page=1), [PR list page 1](https://api.github.com/repos/vue-solana/vue-solana/issues?state=all&per_page=100&page=1), [PR list page 2](https://api.github.com/repos/vue-solana/vue-solana/issues?state=all&per_page=100&page=2)). The docs tell users to open issues and Discussions, but those channels are empty or disabled, which makes the absence of requests a weak negative signal and a strong signal that feedback infrastructure is missing ([contact page](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/contact.md), [Discussions API](https://api.github.com/repos/vue-solana/vue-solana/discussions?per_page=100)). Reddit returned HTTP 403, no public Discord or Telegram channel was found, and general web search was unavailable in this research pass, so the conclusion is “no direct evidence found,” not proof that no Vue developer wants UI ([demand notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Vue%20Solana%20UI%20library/ui-demand-signals.md)).

The strongest proxy demand is wallet-selection UX in neighboring Vue projects, and it is old. `solana-wallets-vue` still has open requests to open a modal programmatically, rename “Select Wallet,” make a component a `type="button"` so it does not submit forms, and repair its copy/disconnect dropdown, while the official wallet-adapter Vue UI came from a 2021 request that produced `WalletModal`, `WalletMultiButton`, and related buttons ([solana-wallets-vue #19](https://github.com/lorisleiva/solana-wallets-vue/issues/19), [#58](https://github.com/lorisleiva/solana-wallets-vue/issues/58), [#57](https://github.com/lorisleiva/solana-wallets-vue/issues/57), [#22](https://github.com/lorisleiva/solana-wallets-vue/issues/22), [wallet-adapter #67](https://github.com/anza-xyz/wallet-adapter/issues/67), [PR #118](https://github.com/anza-xyz/wallet-adapter/pull/118)). Those projects are weak substitutes: `solana-wallets-vue` last released **2025-02-10**, has **31 open issues**, and peer-depends on web3.js v1, while the old `@solana/wallet-adapter-vue-ui` had **9 weekly downloads** in the 2026-11-17..23 window ([solana-wallets-vue repo](https://api.github.com/repos/lorisleiva/solana-wallets-vue), [npm metadata](https://registry.npmjs.org/solana-wallets-vue/latest), [Vue UI npm](https://registry.npmjs.org/@solana%2Fwallet-adapter-vue-ui), [weekly downloads](https://api.npmjs.org/downloads/point/last-week/@solana%2Fwallet-adapter-vue-ui)). Their pain is real, but it is evidence for better wallet state, labels, and slots—not for a frozen visual library under the Vue Solana name.

Inside this repository, the visible UI symptoms are maintainer-observed defects in demo flows rather than component requests. PRs document a QR scanner stuck on “scanning,” Galaxy A50 `BarcodeDetector` failures and missing iOS/Firefox support, Android decoding improving from **40/162 frames at ~175 ms** to **107/162 at ~20–60 ms** after resolution changes, opaque `Solana error #-32002` messages, missing Phantom MWA approval screens with a **120 s** timeout, and signer-card label overflow at 1100/640/390 px ([PR #131](https://github.com/vue-solana/vue-solana/pull/131), [#134](https://github.com/vue-solana/vue-solana/pull/134), [#140](https://github.com/vue-solana/vue-solana/pull/140), [#137](https://github.com/vue-solana/vue-solana/pull/137), [#161](https://github.com/vue-solana/vue-solana/pull/161)). All of those were fixed or explainable in composables, browser-capability handling, localization, or demo CSS. Transaction history also shipped in PR #156 as data only, with no instruction decoding, retries, fee breakdowns, indexing, or explorer UI ([PR #156](https://github.com/vue-solana/vue-solana/pull/156)). That pattern says the missing artifact is a reliable view model and a good example, not a shipped component runtime.

## Styled UI would inherit obligations the headless stack refuses

The product boundary is explicit: core and Vue own Solana state, lifecycle, errors, and Kit integration; apps own labels, layout, theming, and user-facing decisions. The only component in a published package is `SelectedWalletAccountProvider`, a renderless provider that calls `provideSelectedWalletAccount()` and returns `slots.default?.()`, and the Nuxt module registers imports but never components ([SelectedWalletAccountProvider.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/components/SelectedWalletAccountProvider.ts), [Nuxt module](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts), [Nuxt imports](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/imports.ts)). A package that ships text, colors, icons, modal focus management, or toast queues would move responsibilities the repository currently delegates to apps; that is a stance change, not an additive API ([repo-ui notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Vue%20Solana%20UI%20library/repo-ui-surface.md)).

The competitor evidence reinforces the limit. The maintained official UI surface is one React/CSS package, `@solana/wallet-adapter-react-ui@0.9.40`, whose exports are modal/button/icon primitives only—no transaction toasts, account menus, or general dapp UX—and whose modal hardcodes English strings, has a Tab trap limited to `button` elements, and is customized by overriding `.wallet-adapter-*` classes ([react-ui index](https://raw.githubusercontent.com/anza-xyz/wallet-adapter/master/packages/ui/react-ui/src/index.ts), [WalletModal.tsx](https://raw.githubusercontent.com/anza-xyz/wallet-adapter/master/packages/ui/react-ui/src/WalletModal.tsx), [WalletMultiButton.tsx](https://raw.githubusercontent.com/anza-xyz/wallet-adapter/master/packages/ui/react-ui/src/WalletMultiButton.tsx), [styles.css](https://raw.githubusercontent.com/anza-xyz/wallet-adapter/master/packages/ui/react-ui/styles.css), [issue #397](https://github.com/anza-xyz/wallet-adapter/issues/397)). Recurring complaints in that ecosystem are hydration mismatches, wallet-not-detected/stuck states, mobile/deep-link failures, CSS override pain, and historical bundle size—not accessibility; **14 issues** match `SSR`, including the Next.js hydration report #982, while deep-link #385 was closed as out of scope and redirected to MWA ([SSR search](https://api.github.com/search/issues?q=repo%3Aanza-xyz%2Fwallet-adapter+is%3Aissue+SSR&per_page=8), [#982](https://github.com/anza-xyz/wallet-adapter/issues/982), [#385](https://github.com/anza-xyz/wallet-adapter/issues/385), [bundle issue #356](https://github.com/anza-xyz/wallet-adapter/issues/356)). A Vue package could plausibly beat those gaps, but only by accepting the same obligations: a modal must place and trap focus, close on Escape, restore focus, label itself, and avoid false `aria-modal` claims ([W3C ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

The scoring reflects that burden and is deliberately labeled judgment, not measurement. A UI-specific rubric ranked a `ConnectButton` **15/20**, transaction status badge and activity feed **14/20** each, QR wrapper and account menu **12/20**, wallet picker modal **10/20**, token amount input **9/20**, and full design system **5/20**; the earlier 100-point rubric scored built-in UI **54/100** against priority fees at **82** and diagnostics at **76** ([UI feasibility notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Vue%20Solana%20UI%20library/ui-feasibility-strategy.md), [feature rubric](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/strategy-feasibility.md)). The cheap components are thin wrappers; the high-value ones own dialog semantics, wallet icons, mobile handoff, or money input. Reown AppKit is the real full-UI competitor for Vue/Nuxt and Solana, but it brings a project-ID/cloud model, a Solana adapter depending on both Kit and web3.js, and a license restricting commercial use above thresholds—so a lightweight local-first Vue layer is differentiated in principle, but not validated by downloads ([AppKit docs](https://docs.reown.com/appkit/vue/core/installation), [AppKit README](https://raw.githubusercontent.com/reown-com/appkit/main/README.md), [Solana adapter metadata](https://registry.npmjs.org/@reown%2Fappkit-adapter-solana/latest)).

Mechanically, a fourth package is easy to create and expensive to make first-class. The workspace discovers `packages/*`, but export-map checks, pack-size budgets, standalone-install smoke tests, externals checks, lean-import graphs, bundle reports, TypeScript aliases, and Vitest aliases are hard-coded around core/vue/nuxt; a UI package must be added to each or ship without the protections the project relies on ([workspace](https://github.com/vue-solana/vue-solana/blob/main/pnpm-workspace.yaml), [check-exports-map.mjs](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-exports-map.mjs), [check-pack-size.mjs](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-pack-size.mjs), [smoke matrix](https://github.com/vue-solana/vue-solana/blob/main/scripts/smoke-standalone-installs.mjs), [check-externals.ts](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-externals.ts), [check-lean-imports.mjs](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-lean-imports.mjs)). The Vue release build already batches declaration rollup because one pass needs more than 8 GB, and component entries add build pressure ([build.release.config.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/build.release.config.ts)). Every docs addition must be mirrored structurally into `de/es/fr/ja/ko/zh` under a hard test, and `apps/docs` pins a published version, so a new package cannot be demonstrated in docs until after release ([locale-docs.test.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/locale-docs.test.ts), [docs package policy](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/docs-package-policy.test.ts)). No local policy defines a UI tarball or eager-chunk budget, and no CI job checks accessibility, CSS output, icons, or visual regressions today ([repo-ui notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Vue%20Solana%20UI%20library/repo-ui-surface.md)).

## Kit leaves gaps in state and policy, not in pixels

The better new-feature queue follows what Kit deliberately does not own. Kit 8.x supplies typed RPC, subscriptions, account codecs, transaction planning/sending, priority-fee primitives, and generated program clients, while official plugins remain 0.x; Vue value comes from reactivity, cancellation, stale data, SSR boundaries, and policy ([Kit README](https://github.com/anza-xyz/kit/blob/main/README.md), [kit-ecosystem notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Next%20Vue%20Solana%20feature/kit-ecosystem.md)). The official wallet plugin now covers discovery, reconnect, account selection, signer/payer mapping, SIWS, and verification but ships React hooks only and explicitly tells Vue users to write a `shallowRef` integration; adding it alongside the existing registry would create two discovery lists, two selected-account states, two reconnect policies, and two payer mappings ([plugin README](https://raw.githubusercontent.com/anza-xyz/kit-plugins/main/packages/kit-plugin-wallet/README.md), [plugin npm](https://registry.npmjs.org/@solana%2Fkit-plugin-wallet)). Treat it as a reference for warm-up gating, account verification, and SSR-safe stubs, not as a dependency to graft onto the working MWA/iOS layer.

That ordering also explains why a UI package is not the answer to “what’s next.” Transaction history is already stable and e2e-covered; a read-only activity list can be a thin consumer of `useTransactionHistory()` without decoding, retries, or explorer presets ([archived plan](https://github.com/vue-solana/vue-solana/blob/main/plans/archived/transaction-history.md), [Vue panel](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/TransactionHistoryPanel.vue), [e2e spec](https://github.com/vue-solana/vue-solana/blob/main/e2e/example-apps.spec.ts)). A connect button is the natural next component because onboarding value is high, but it inherits wallet-status, error, and mobile-handoff states; a picker modal is last because it cannot avoid dialog a11y, wallet icons, and platform redirects ([WalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/examples/vue-vite/src/components/panels/WalletPanel.vue), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). An activity list first, connect button second, and picker last is the risk ordering, even if a maintainer chooses to publish two components initially.

## Earn the package with evidence, then keep it thin

The immediate plan should be documentation and examples, not a new version surface. Add one short “UI recipes” section to the existing wallets guide and one to the transactions guide, with copyable SFCs for a connect button plus wallet list, account chip, transaction status badge, and read-only activity list based on the exact patterns in `WalletPanel.vue`, `DemoWalletPanel.vue`, and `TransactionHistoryPanel.vue` ([wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md), [transactions guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/transactions.md), [DemoWalletPanel.vue](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/app/components/demo/DemoWalletPanel.vue)). Polish the example panels and make their `data-testid`s, disabled states, and ARIA assertions the canonical recipe contract; add a derived wallet status/error formatter to `@vue-solana/vue` only where recipe code demonstrably duplicates logic, keeping it subpath-safe and dependency-free ([e2e spec](https://github.com/vue-solana/vue-solana/blob/main/e2e/example-apps.spec.ts), [use-execution.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/vue/src/composables/use-execution.ts)). Mirror every new section into all six locale trees with identical heading order and code-fence counts, and regenerate the tracked LLM surface only when English content actually changes ([locale-docs.test.ts](https://github.com/vue-solana/vue-solana/blob/main/packages/core/src/locale-docs.test.ts)).

Publish UI only when a clear set of conditions holds: repeated external demand, proven duplication, and an owner for the long tail. The proposed bar is **three unsolicited requests for the same component, or two independent apps—one external—maintaining materially identical DOM/CSS/interaction markup**; underlying composables should remain stable for one release; a named maintainer must accept keyboard/focus tests, theming, translated docs strings, and visual baselines; and any connect or picker component must be exercised through real Android MWA, iOS browser wallet, and desktop Wallet Standard flows ([UI feasibility notes](https://github.com/vue-solana/vue-solana/blob/main/research_notes/Vue%20Solana%20UI%20library/ui-feasibility-strategy.md), [W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [wallets guide](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/guides/wallets.md)). Because the current feedback channels are empty or disabled, add a docs feedback link for UI recipe requests first; otherwise the trigger cannot be measured ([contact page](https://github.com/vue-solana/vue-solana/blob/main/apps/docs/content/contact.md), [Discussions API](https://api.github.com/repos/vue-solana/vue-solana/discussions?per_page=100)).

If a package is mandated despite that evidence, constrain it hard: an opt-in `@vue-solana/ui@0.x`, ESM-only, `sideEffects: false`, exact `types`/`import` subpaths, `vue` plus existing workspace packages only, and no root re-export that drags UI into the three existing roots. Ship slot-driven `WalletConnect`, `TransactionStatus`, and a read-only `ActivityList` with class/data-attribute hooks, consumer-supplied labels and ARIA text, no CSS file, no design tokens, no icon set, no modal portal, no focus trap, no toast queue, no QR camera component, no token input, no account menu, no wallet SDK, and no promise about mobile handoff; browser-only work stays in existing composables and app lifecycle ([ESM export rules](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-exports-map.mjs), [lean-import rules](https://github.com/vue-solana/vue-solana/blob/main/scripts/check-lean-imports.mjs), [Nuxt module](https://github.com/vue-solana/vue-solana/blob/main/packages/nuxt/src/module.ts)). Test roles, disabled states, and emitted actions functionally on both example apps; defer screenshot baselines until a CSS contract exists ([Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)). This is a viable package, but it is deliberately a small one—and it remains a later bet, not the next release.

## Conclusion

The UI-library question is really two unresolved questions in disguise: who owns presentation, and how does this project hear from users? The absence of an active Vue-native Solana UI competitor is an opening, not a mandate; category-defining packages require evidence, not just an empty shelf. Opening a lightweight feedback channel and watching whether the same recipe is copied by external apps would turn the next UI decision from maintainer intuition into measurement.

The compounding advantage is a headless surface so predictable that Nuxt UI, shadcn-vue, Vuetify, or plain CSS can sit on top without negotiation. The docs and examples should make the first ten minutes feel finished while keeping visual choices in app code; that delivers the UX win now without freezing a visual contract or splitting a single-Kit, lean-bundle, seven-locale release machine. A UI package remains a reasonable future option, but only as a thin consumer of stable composables and proven duplication—never as the vehicle for rethinking wallet, client, or release architecture.
