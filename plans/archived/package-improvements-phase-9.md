# Package Improvements Plan — Phase 9 (archived)

> **Archived.** Phase 9 is complete: all 24 tasks are checked and each carries a `Resolved:` note naming the regression test or gate that would fail if it were reverted. Phases 1–8 live in [`package-improvements-phases-1-8.md`](./package-improvements-phases-1-8.md).

Tracks the Phase 9 review follow-ups for `@vue-solana/core`, `@vue-solana/vue`, and `@vue-solana/nuxt`. Kept as the record; no items remain open.

Phases 1–8 of the original 2026-10-06 three-package audit are complete and shipped in 4.0.0; that record lives in [`package-improvements-phases-1-8.md`](./package-improvements-phases-1-8.md). Phase 9 (the 2026-10-21 post-`rc.0` branch review) was the last open phase and is now complete, so this file is archived with it.

Rules that applied:

- Do not split the existing public API to fix these items. Fixes must preserve the unified `useWallets()` / `useWallet()` flow, the full `kit` mirror subpaths, and the ESM-only module format.
- When an item is implemented, check its box and append a `Resolved:` note saying what landed and which test would fail if it were reverted. Keep all items in place — the closed ones are the record.
- Every error composables throw is core's `SolanaError`; `isSolanaError()` must stay true for them.
- Core stays DOM-free; browser APIs live in `@vue-solana/vue`.
- Nuxt never accepts or forwards `payer` / `payerSecretKey`.

## [x] Phase 9: 4.0.0 Release Review Follow-Ups — P0

Status: complete (2026-11-13). All 24 items landed; each closed item carries a `Resolved:` note naming the regression test or gate that would fail if it were reverted. Source: full-branch review of `@vue-solana/core@3.0.1...HEAD` (142 files, 18 commits, `HEAD` = `1553c9e`) on `release/v4.0.0`, re-verified against `main` on 2026-11-13. Every gate passes (`format`, `lint`, `test`, `typecheck` all six projects, `build:packages`, `build:examples`, `--filter docs build`, `pack:size`, `check:entries`, `check:esm-map`, `check:externals`, `check:buffer-polyfill-declarations`, `size:packages`, and `test:e2e` — 32 specs), so these were review-level defects, not build failures. Each item landed as its own change set.

The 4.0.0 branch has since shipped (`4.1.11` is the current version), so the original pre-mode instructions no longer apply: `.changeset/bundle-size-trim.md` was consumed at release and every behavior fix now needs its own changeset, with user-facing notes folded into it. The behavior changes here are recorded in `.changeset/consistent-error-codes.md`.

Tasks:

**P0 — correctness**

- [x] `confirmTransactionSignature()` ignores custom abort reasons. `packages/core/src/transaction.ts:150-156` only rethrows when `isAbortErrorLike()` sees `name === "AbortError"` (`transaction.ts:195-201`), but `wait()` rejects with `signal.reason` (`transaction.ts:186-189`) and `throwIfAborted()` throws it verbatim. `controller.abort(new Error("navigation"))` therefore surfaces as `RPC_FAILURE`, contradicting `packages/core/src/types.ts:173` (“rejects with the signal's reason”). Fix: in the catch, `if (abortSignal?.aborted) throw abortSignal.reason;` before the name check. Add the custom-reason regression test under P2 below. Resolved: implemented as `throw abortSignal.reason ?? cause` (the fallback keeps non-conforming signals that report `undefined` from rejecting with `undefined`), covered by `transaction.test.ts` “rejects with the caller-supplied abort reason”.
- [x] Wallet failure paths became silent. This branch replaced every diagnostic `console.error` with `void cause;`: mobile-wallet registration (`packages/vue/src/plugin.ts:178-180`), persisted-wallet auto-connect (`plugin.ts:218-220`), initial `refreshWallets()` (`plugin.ts:272-274`), and the iOS callback (`packages/vue/src/plugin/wallet-registry.ts:131-137`, i.e. decryption / deep-link errors). None sets `error.value` and none logs, while RPC and storage failures still do (`plugin.ts:103-110`, `133-135`). Keep the `console.info` removal, but restore observability: set `error.value = normalizeSolanaError(cause, ...)` where a context exists and add a dev-only `console.error` or injectable logger. The iOS callback is the highest-value path. Resolved: all four paths set `error.value` and log through `logDevError()` (dev-only, `[Vue Solana]` prefix). The code is `WALLET_FAILURE` (new, below) rather than `RPC_FAILURE`. The bootstrap now starts `checkConnection()` before `refreshWallets()`, because `checkConnection()` clears the shared `error` ref synchronously and used to wipe the refresh failure in the same task.

**P1 — security hardening and precedence**

- [x] `signIn` verifies the wallet-returned account, not the active one. `packages/core/src/wallet-standard/adapter.ts:151-158` verifies `signInResult.account.publicKey`, while `signMessage` correctly verifies `getActiveAccount(account).publicKey` (`adapter.ts:175-180`). When `input` is omitted the default input is built from the active account (`adapter.ts:144`), so a wallet returning a different account it controls passes the client check. Server-side SIWS verification still gates trust, but this is an account-substitution hole and an inconsistency. Fix: when `input?.address` is absent, verify the active account; when present, require the returned account to match `input.address`; reject any returned account absent from `wallet.accounts`. Resolved: the adapter now rejects a returned account absent from `accounts` (`INVALID_SIGNATURE`), rejects a mismatch with `input?.address ?? account?.address`, and verifies against the exposed account's `publicKey`. Covered by “rejects a sign-in result for a different account than the active one” and “…for an account the wallet does not expose”.
- [x] Malformed signatures skip the length check when Ed25519 WebCrypto is unavailable. `packages/core/src/wallet-standard/verify-wallet-signature.ts:27-49` attempts `importKey` first and returns from the catch (line 38) before `isSignatureBytes(signature)` (line 44). On older Safari or an insecure context a wallet returning a 3-byte signature is accepted silently instead of throwing `INVALID_SIGNATURE`; the length check is crypto-independent. Fix: move the `isSignatureBytes` branch above the `importKey` try/catch. The existing fallback test (`packages/core/src/wallet-standard/adapter.test.ts:670`) uses a 64-byte signature, so it cannot catch this. Resolved: length check moved first; covered by “rejects a malformed message signature even where Ed25519 WebCrypto is unavailable”.
- [x] Nuxt inline module options equal to a default lose to public config. `packages/nuxt/src/module.ts:147-173` detects an “untouched default” by comparing `options[key]` with `MODULE_DEFAULTS[key]` (`module.ts:54`) and checking `nuxt.options.solana`. Inline options (`modules: [["@vue-solana/nuxt", { cluster: "devnet" }]]`) never appear in `nuxt.options.solana`, so an explicit value equal to the default is treated as untouched and `runtimeConfig.public.solana.cluster` wins. The `solana` config-key path is covered (`packages/nuxt/src/module.integration.test.ts:102`); the inline path is not. Fix: apply per-key defaults only after the merge for every key where explicitness matters (`cluster`, `autoConnect`), so `undefined` means “not set”, and add the inline-options integration case. Resolved: `defineNuxtModule` no longer declares `defaults`; `mergeSolanaSources()` applies `MODULE_DEFAULTS` only for keys nothing else defined. `nuxt.options.solana` therefore no longer carries those two defaults (they remain in `runtimeConfig.public.solana`). Covered by the integration cases “lets inline options equal to a default win over public.solana” (fails before the fix) and “lets an inline autoConnect option win over public.solana”, plus the unit cases reworked for the real merge shape.

**P2 — consistency, edge cases, tooling**

- [x] `toAddressInput()` recursion has no cycle guard. `packages/core/src/address.ts:39-58` unwraps getters and `{ value }` refs recursively, so `const a = () => a` throws `RangeError: Maximum call stack size exceeded` instead of `INVALID_ADDRESS`. Add a depth limit (e.g. 32) and throw a `SolanaError` with `INVALID_ADDRESS` when exceeded. Resolved: `toAddressInput()` takes a depth argument and all three recursive paths (getter, ref, nested ref) increment it; past 32 levels it throws `INVALID_ADDRESS` with a “possible cycle” message. Covered by `address.test.ts` “throws INVALID_ADDRESS for cyclic getters and refs instead of overflowing the stack” (a `RangeError` before the fix) plus “unwraps legitimate nesting up to the depth limit” so the budget is not accidentally tightened.
- [x] `useSignatureStatus` reports invalid input as `RPC_FAILURE`. `packages/vue/src/composables/useSignatureStatus.ts:146-147` uses `RPC_FAILURE` for `pollIntervalMs <= 0`, while core uses `INVALID_INPUT` for the same class (`packages/core/src/transaction.ts:89-94`, `timeout.ts`). Recommended: switch to `INVALID_INPUT` and update `apps/docs/content/packages/vue.md:840`, `knowledge-bundle/packages/vue.md:396`, and the three locale files in the same change set. This is a small behavior change, so record it in the changeset. Resolved: now `INVALID_INPUT`; `useSignatureStatus.test.ts` asserts it, and the English, knowledge-bundle, and all six locale copies document it. A malformed _signature_ still reports `RPC_FAILURE` — only the option changed. Recorded in `.changeset/consistent-error-codes.md`.
- [x] Wallet-signing composables still report `RPC_FAILURE` for wallet-only failures. `useSignMessage`, `useSignIn`, and `useSignTransactions` share `useExecution`'s `RPC_FAILURE` fallback (`packages/vue/src/composables/use-execution.ts:65`), while `useWallet()` and the plugin boot paths now use `WALLET_FAILURE`. Parameterize the fallback code per composable (the sign-and-send composables mix wallet and RPC failures, so decide those separately) and update the tests that assert `RPC_FAILURE`. Resolved: `useExecution()` takes a `failureCode` option (default `RPC_FAILURE`); the three wallet-only composables pass `WALLET_FAILURE`. The sign-and-send pair keeps the RPC default on purpose — it does reach the network — and relies on the specific codes thrown before the RPC call. Tests: the renamed `useSignMessage` case plus new generic-failure cases in `useSignIn.test.ts` and `useSignTransactions.test.ts`.
- [x] `Taskfile.yml` release-tool nits. `Taskfile.yml:102` and `:111` write `${{.RC_TAG}}`; Task renders `{{.RC_TAG}}` to `rc`, leaving the shell to expand an empty `$rc`, so the messages read `does not match the  tag` and `publishing : 4.0.0-rc.0`. Use `{{.RC_TAG}}` like line 113. Also `rc:finalize` (`Taskfile.yml:140-149`) deliberately runs outside pre mode, so running it on `main` consumes the pending changeset and cuts a final version; add a branch confirmation or precondition. Resolved: both messages use `{{.RC_TAG}}`; `rc:finalize` gained two preconditions — `CONFIRM=1` and at least one pending changeset — so it refuses (`precondition not met`) before touching a file. `task --list` still parses the file. A hard `main`-branch check was rejected: it would break the documented flow of cutting the final version from a release branch before merging.

## Suggested Implementation Order

All items landed on 2026-11-13; the order below is the record of how they were sequenced, one change set each:

1. P2 correctness: `toAddressInput()` cycle guard (with a regression test).
2. P2 consistency: `useSignatureStatus` `INVALID_INPUT`, then the wallet-signing `RPC_FAILURE` → `WALLET_FAILURE` decision.
3. Tests: SWR eviction cap, commitment-on-the-wire, misnamed `clusters.test.ts` case.
4. Documentation: `MISSING_CLIENT_CAPABILITY`, `deleteSwrKey()` on the docs site, the Nuxt SWR auto-import claim — one change set per doc family, mirroring all locales.
5. Tooling: `Taskfile.yml` `RC_TAG` messages and the `rc:finalize` confirmation precondition.
6. `waitForRedirect` export decision and the stale “four colliding names” count.

Documentation and tooling items were independent and ran in parallel with the code items.

## Decisions

- `useConnection()` / `useSolanaConnection()` stays through 4.x: removal target 5.0.0. Deprecated since 2.0.0, but removing it now would churn both example apps, the package READMEs, and the four locale doc trees for no functional gain.
- `waitForRedirect()` became public API: exported from `packages/core/src/ios-wallet.ts` with `WaitForRedirectOptions` and documented, rather than rewording the 4.0.0 changelog entry. The export is additive, and a custom iOS deep-link flow genuinely needs the timeout/abort escape hatch.

Resolved decisions from the 4.0.0 audit (commitment config, `MissingClientCapabilityError` hierarchy, SWR eviction policy, `buffer` packaging, iOS lazy-load deferral, abort-reason passthrough, `WALLET_FAILURE`) are recorded in [`package-improvements-phases-1-8.md`](./package-improvements-phases-1-8.md).
